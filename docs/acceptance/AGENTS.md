# acceptance/ — 验收规程

约束本目录。本目录回答一个问题：**一个工作项要凭什么才允许离开 `review/`。**

## 1. 验收不是测试

| | 测试 | 验收 |
|---|---|---|
| 问的问题 | 代码按我写的逻辑跑了吗 | **说书人和玩家能不能真的玩完一局** |
| 载体 | `tests/` | 本目录的规程 + 一次真实会话 |
| 谁判 | 测试框架 | 代理自己按矩阵逐行判，写出结论 |
| 全绿意味着 | 这行不通过 | — |

**测试全绿不是验收。** 一个规则内核可以把 300 个单元测试跑绿，
而说书人在第一晚唤醒占卜师时发现界面根本没让你选"干扰项"。

## 2. 当前状态：对局载体已起步，验收批次尚待跑（诚实记录）

2026-10-02 起 `web/` 已落地（单 SPA 两套视图，D-0018）：说书人上帝视角面板可连真宿主、
真 SignalR、真 SQLite 做一次**单客户端**会话（`tools/verify-storyteller-panel.mjs`：
分配 → 开夜 → 推送推进 → 状态上报与归因，21 项断言 + 5 张截图；`npm run gate` 另有
23 条前端单测）。因此：

- **载体已具备**：一次构建 + 一次多客户端会话可以做起来了；`web/src/features/player/**`
  是玩家端骨架（加入 / 收请求 / 提交 / 看自己的信息类结果），但**尚未**进入验收批次；
- **尚未跑过验收批次**：`review/` 里三张票据（结算引擎、夜晚顺序表、步骤机）的行结论仍停留在
  "协议层通过 / 缺玩家端"的状态，不许用"真机冒烟全绿"顶替它们；
- **面向玩法的票据**（其期望只能用一次完整对局来证明）在跑完批次之前仍不满足验收条件，
  只能停在 `review/` 并写明缺什么；
- **不依赖对局的票据**（工具、数据、文档）按自身矩阵逐行判定，结论只有"通过 / 不通过 /
  无法判定"三种，证据摘要按 `docs/evidence/verification.md` 留档。

这不是偷懒，是 `docs/backlog/README.md` 规定的"等待是诚实的状态"。

## 3. 验收批次

验收按**批次**跑，不按票据跑。一次会话（一次启动 + 一次多客户端联机）尽可能覆盖所有
等待中的票据，因为"一票一会话"是成本最高的循环。

- 一批 = 一次构建 + 一次部署 + 一次多客户端会话；
- 一批能覆盖的票据，全部在同一批里判完；
- 判不了的票据**留在 `review/`** 并写明缺的能力，不许含糊放行；
- **批次的骨架已存在**：`tools/verify-storyteller-panel.mjs` 已经是"起真宿主 + 真浏览器 +
  真数据库"的一套装置，加玩家客户端（同一 SPA 的 `#player`）即可扩成多客户端批次。

## 4. 验收矩阵的维度

任何一个面向玩法的能力，都必须按这四个维度展开，而不是只测"快乐路径"：

| 维度 | 展开 |
|---|---|
| **角色** | 该能力的角色 + 与其有相克规则的角色 + 会改变它的角色 |
| **方向** | 能力作用于别人 / 别人作用于它（对称吗） |
| **视角** | 说书人视图 / 当事玩家视图 / **无关玩家视图**（无关玩家绝不能看出端倪） |
| **相关族** | 同类机制的其他角色是否同病（`AGENTS.md`：修复要整族对齐） |

第三行是本项目最容易漏的：**信息隔离的验收必须是"不该看见的人确实没看见"**，
而不只是"该看见的人看见了"。

## 5. 判一行的规则

一行验收的结论只有三种，且必须给出**这一次运行**的证据：

| 结论 | 条件 | 票据去向 |
|---|---|---|
| 通过 | 有该行的运行时证据（截图 / 日志 / 会话记录） | 累计后进 `done/` |
| 不通过 | 证据显示行为与期望不符 | 移回 `todo/`，票据标 `Rejected` |
| 无法判定 | 缺依赖或缺执行能力 | **留在 `review/`** 并写明缺什么 |

**没有第四种。**「大致符合」「看起来没问题」「单元测试覆盖了」都不是结论。

## 6. 残余事项

判不了的行不许消失，必须写成**残余事项**留在票据里，并说明：
缺什么能力、什么时候能补、由谁补（人或代理）。
