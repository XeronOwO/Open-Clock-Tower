# 生效中的决策

> 每条决策必须写明**背景 → 选项 → 选择 → 因此带来的代价**。
> 只写"选了 A"而不写"放弃了什么"的决策，等于没有决策。

---

## D-0001 产品形态：完整线上平台

- **状态**：Accepted
- **背景**：官方魔典只做基础标记；断线不自动重连、状态会不同步。需求方要建网站平台解决这两类痛点。
- **选项**：
  - A. 完整线上平台：说书人端 + 每名玩家各自的设备端，服务端权威状态。
  - B. 只说书人端"智能魔典"：玩家在线下或外部语音里玩。
  - C. 先做 B，玩家端二期接入同一内核。
- **选择**：**A**。
- **代价**：必须做两套客户端、服务端强制信息隔离、以及真正的重连协议。
  这三件事在方案 B 里都不存在。选 A 就是选了这个成本。

## D-0002 自动化边界：记录 + 校验 + 推演

- **状态**：Accepted
- **背景**：游戏里存在大量说书人自由裁量点（占卜师的干扰项选谁、醉酒玩家看到什么假信息、
  陌客/间谍被当作什么、疯狂是否成立、是否处决、相克规则未覆盖时怎么办）。
- **依据**：百科《重要细节》一-2 明确"说书人的言语即是游戏规则"，且疯狂等机制
  "由说书人做最终裁决"。
- **选项**：
  - A. 记录 + 校验 + 推演：平台算出"此处需你决定"，给全部合法选项与后果预览，说书人拍板，
    平台记录并自动推演后续链式反应。
  - B. 在 A 之上加"智能建议"（按胜率/趣味性推荐并高亮）。
  - C. 全自动：连裁量点也由平台决定。
- **选择**：**A**。
- **代价**：平台不能承诺"全自动主持"。说书人仍然必须在场逐步拍板。
  换来的是与官方设计理念一致、且**每一条裁定都可追溯、可回归测试**。
- **推论**：内核必须把"裁量点"设计成一等的输入契约，而不是让角色代码自己 `Random`。
  这是 D-0008（内核确定性）的直接来源。

## D-0003 首版剧本覆盖：《梦殒春宵》全集

- **状态**：Accepted
- **背景**：百科有 400+ 角色页、400+ 条相克规则；需求方实际常玩《梦殒春宵》。
- **选项**：A. 仅《暗流涌动》（最容易）；B. 官方三剧本；C. 全量（含实验性/传奇/社区剧本）。
- **选择**：**《梦殒春宵》(`sects-and-violets`)，25 个角色全集**。
- **代价与风险（必须正视）**：《梦殒春宵》是官方三剧本里**裁量与状态变化最密集**的一个——
  它同时引入**疯狂**、**阵营转变**、**角色交换**、**动态检测**四条最复杂的机制链，
  以及大量爪牙/恶魔之间的相克规则。选它意味着首版就得把这四条链做对，
  不能像选《暗流涌动》那样先做一个"逻辑干净"的版本。
  应对：把四条链拆成内核里各自独立的机制模块，用《梦殒春宵》25 角色做**全量验收矩阵**，
  而不是逐个角色打补丁。
- **反面选项为何不选**：A 会让实际使用场景（常玩梦殒春宵）无法落地；
  C 的工作量是数量级差距，且百科自身对三角色相克都还没整理。

## D-0004 技术底座

- **状态**：Accepted
- **选择**：
  - 后端 ASP.NET Core；前端 Vue 3 + TypeScript（需求方指定）。
  - 实时通道 **SignalR**（ASP.NET Core 原生，自带重连与分组语义）。
  - 持久化 **SQLite**（EF Core），**provider 可换**：数据访问层不得出现 SQLite 方言、
    不得用只有 SQLite 才有的特性（如 `AUTOINCREMENT` 专有写法、无类型列的隐式转换）作为设计前提。
  - 前后端契约由 OpenAPI 生成 TypeScript 客户端，禁止手工维护两份 DTO。
- **代价**：SQLite 的写并发能力弱，因此持久化设计必须**串行化单局写路径**（一局游戏的写入是单写者），
  这一点反而与"事件溯源 + 服务端权威"天然契合。

## D-0005 规模约束：小圈子自用、MIT 开源

- **状态**：Accepted
- **背景**：需求方明确"小圈子游玩、代码全部开源、暂不考虑公开服务"。
- **选择**：**不做**多实例、高并发、多级缓存、分布式一致性、独立消息队列。
  存档与对局数据以**单机可完整运行**为前提设计。
- **代价与红线**：*规模小* **不等于** *可以不安全*。信息隔离是**游戏规则的一部分**
  （玩家不该知道自己不该知道的东西），必须在服务端强制，不能因为"都是熟人"而降级。
  参见 D-0009。

## D-0006 语言策略：中文优先

- **状态**：Superseded by D-0016（语言条款整体；标识符按术语表的英文 slug 规则保留）
- **背景**：参考项目 CUO 的规则是"提交内容用英文 + 人工文档 en/zh 双语镜像"。
  但本项目的领域词汇（角色名、机制名）以**中文百科**为唯一权威来源，双语全量镜像等于双倍成本。
- **选择**：
  - 代码、标识符、注释、提交信息、日志**用英文**。
  - 人工文档与界面**用中文**；目录沿用 `docs/`，**暂不建 `docs/en/` 镜像**。
  - 角色/机制一律「英文 slug + 中文名」成对，以 `docs/standard/terminology.md` 为准。
- **代价**：**偏离参考项目的双语门禁**。将来若要国际化，需要补建 `docs/en/` 并重新承担对齐成本。
  这是一次**有意识的偏离**，不是疏漏。

## D-0007 美术资源：运行期热链百科图片

- **状态**：Accepted（已落地：魔典席位牌角色图，2026-10-04；实测结果见 `rulings.md` R-0006）
- **背景**：官方立绘/标记图是 TPI 与集石的版权资产；本项目 MIT 开源，不能提交进仓库。
- **选项**：
  - A. 自绘/抽象图标 + 文本（仓库最干净）。
  - B. 支持本地素材包（运行时从本地目录加载）。
  - C. 运行期热链百科图片（不落库）。
- **选择**：**C**。
- **落地形态**：`web/src/display/character-art.ts`（25 人 slug → 百科图片地址；路径由角色页首行
  `[[File:…]]` 的文件名按 MediaWiki md5 规则派生）+ `web/src/features/grimoire/CharacterArt.vue`
  （`referrerpolicy="no-referrer"`；`@error` 撤图）。探针 `tools/check-character-art.mjs`
  （正常加载 / 阻断降级 / 未知不请求 / 局域网 origin + 移动端仿真）。
- **代价**：
  1. 依赖外部站点的可用性——百科挂了/改了图片路径，界面就退化（降级为文字 + 色环，不裂图）。
  2. 防盗链（Referer 校验）与跨域限制：**2026-10-04 实测无防盗链、`<img>` 无需 CORS**（R-0006）。
- **强制对冲（不是可选项）**：前端**必须**实现图片加载失败降级——显示角色名 + 阵营色块。
  任何情况下不得留白、不得裂图（已落地：`CharacterArt.vue` 的 `@error` 撤图，外层文字 + 色环保留）。
  仓库内**永远不出现**官方图片文件。

## D-0008 规则内核确定性

- **状态**：Accepted
- **背景**：平台要支持"说书人执行错了要能回退/撤销"，还要能复盘整局。
  若内核里存在时间、随机数、IO、迭代顺序不确定等来源，回放就会漂移，撤销就不可信。
- **选择**：
  - `Kernel` 是**纯计算**：给定（状态 + 说书人裁定输入序列），必产出**逐字节一致**的结果。
  - 内核内**禁止**：`DateTime.Now`、`Random`、文件/网络 IO、`Guid.NewGuid`、
    依赖 `Dictionary` 枚举顺序作为结算顺序。
  - 所有随机性只允许出现在**裁定点**，且随机结果由说书人裁定或由外部注入的种子决定。
  - 时间只以"逻辑时刻"（第几个白天/夜晚、第几个结算步）进入内核，真实时间只在应用层使用。
- **代价**：角色实现写起来比"随手 `Random`"麻烦；每个裁定点都要显式建模。
  换来的是撤销、回放、断线重连三件事都变成同一套机制的自然结果，而不是三套互相打架的补丁。

## D-0009 事件溯源 + 服务端强制视角投影

- **状态**：Accepted
- **背景**：两个需求同时指向同一套机制——"断线重连不丢状态"与"玩家只能看到自己该看的"。
- **选择**：
  - 状态由**命令 → 事件 → 投影**产生；事件是唯一事实来源，当前状态是可重建的派生结果。
  - **视角投影在服务端强制**：同一份事件流，按接收者产出说书人视图 / 各玩家视图。
    玩家端拿不到的资料，**根本不会下发**（不是"前端不显示"）。
  - **撤销** = 截断到指定事件序号后重放，并保留审计轨迹；**不删除历史事件**。
- **代价**：投影层要按视角写多份，且每加一种信息就要重新审一遍"谁能看见"。
  但这是唯一能同时满足两个需求的正路；"前端隐藏"式的实现会在玩家打开开发者工具时立刻失效。

## D-0010 重连语义：快照 + 全量补齐

- **状态**：Accepted
- **背景**：官方魔典的痛点就是断线后状态不同步且不自动重连。
- **选择**：
  - 重连时客户端出示**会话票据**，服务端校验后返回：
    1. 一个**快照**（含快照对应的事件序号 `N`）；
    2. **从 `N` 起的全部事件**，按序补齐。
  - 命令携带**客户端序号 + 幂等键**，重复提交不产生重复效果。
  - 事件序号**单调递增**；客户端发现缺口即主动请求补齐，而不是继续前进。
- **明确禁止**（这是本项目最容易走歪的地方）：
  - 禁止"本地先跑 N 秒再跟随"；
  - 禁止"延迟窗口""保护期""先按本地状态渲染再慢慢对齐"；
  - 禁止新旧两套同步机制共存来掩盖分叉。
- **代价**：长局的事件量会让重连补包变大，需要**定期快照**来控制重连成本。
  这个代价是明账——用快照周期换正确性，而不是用时间窗口换正确性。

## D-0011 自动步骤系统：操作请求（Operation Request）

- **状态**：Accepted
- **背景**：需求方补充要求——做一套"类似狼人杀"的自动步骤系统：轮到某名玩家发动技能时，
  由服务端**主动向他推送操作请求**；操作请求**暂不设计超时时间**。
- **选项**：
  - A. 客户端轮询"现在轮到我了吗"。
  - B. 服务端把"需要某人做决定"建模成一等对象，**定向推送**给该玩家。
- **选择**：**B**。并把两件事明确分开：

  | | 面向谁 | 载体 |
  |---|---|---|
  | `DecisionPoint` 裁定点 | **说书人** | 前述 D-0002：记录 + 校验 + 推演 |
  | `OperationRequest` 操作请求 | **玩家** | 本决策：推送 + 校验 + 挂起 |

  两者同源于同一个内核原语（"有人必须做一个选择"），只是受众与投影不同。

- **硬约束**：
  1. 请求由**服务端发起**，走 SignalR 定向到该玩家的连接；客户端不轮询、不自行推断轮次。
  2. 请求**持久化在服务端**。断线重连后必须**重新投递**——这是"自动重连"的内在部分，不是附加功能。
  3. **暂不设超时**：内核里不存在"过期时间"这个概念，只存在**作废原因**。
     请求一直有效，直到被响应、或被上游状态变化作废。
- **代价（必须正视）**：
  - 无超时 = **一个挂机的玩家能无限期卡住整局**。因此下面三件事不是可选项：
    说书人可**强制作废 / 代填**该请求；说书人端有**谁在卡着**的可见列表；每次作废都记录原因。
  - 请求-响应是异步的，结算引擎必须能**暂停在一个挂起点并把该挂起状态持久化**，
    不能靠"内存里挂着一个长连接等待"——那样一重启整局就废了。
- **部署提示**：`SignalR` 的 WebSocket 长连接在开发期需显式启用（`UseWebSockets`），
  且重连靠的是"票据换快照+补齐"，不是靠连接本身活着。

## D-0012 零信任安全模型

- **状态**：Accepted
- **背景**：需求方补充要求——"虽然是私下里的小服务，也要考虑服务安全性，做好鉴权等操作，
  在信息、操作方面做好校验，对客户端采取零信任准则"。
- **选择**：把**零信任**作为一条架构不变量，而不是一堆散落的检查：

  1. **客户端的一切输入都不被信任**——包括"我是几号玩家""我的角色是什么""我投了谁"。
     服务端只信**自己推导出的状态**。客户端发来的身份声明只用于**定位会话**，不用于**授权**。
  2. **鉴权分两层**：
     - 会话票据 `SessionTicket`：证明"你是这一局的哪一名玩家"；
     - 连接绑定的**私有凭据**：加入时下发、只在下发它的那条连接上有效；重连必须重新出示。
  3. **操作校验：四道闸**，全过才允许进内核——
     | 闸 | 问题 |
     |---|---|
     | 身份闸 | 你是谁，你在本局是什么身份 |
     | 阶段闸 | 现在是哪个阶段，轮到你了吗，这个请求是发给你的吗 |
     | 合法性闸 | 你提交的选项在服务端算出的合法集合里吗 |
     | 幂等闸 | 这个命令是不是重复投递（幂等键 + 客户端序号） |
  4. **信息校验只在下发方向做**：服务端按接收者投影，**越权信息根本不下发**。
     绝不依赖"前端不显示"——那在开发者工具面前一秒失效。
  5. **前端把服务端数据当不可信输入**：长度、类型、范围都要防御性处理与渲染。

- **代价**：
  - 每加一个命令都要写四道闸的判定，开发成本显著上升；
  - 换来的是**客户端被完全攻陷也无法作弊或窃取他人信息**——对一款"信息就是胜负"的游戏，
    这个代价必须付。
- **不是漏洞的部分**：玩家在自己设备上能看到**自己**的全部信息（含自己被要求疯狂证明什么），
  这是规则允许的，属于设计而非缺陷。

## D-0013 防场外：恒定夜晚节奏（时序不泄漏）

- **状态**：Accepted
- **背景**：需求方指出——如果"空过"的角色（例如夜间行动角色已全部死亡）不占时间，
  夜晚就会因为"实际有几个技能位"而变长变短；好人可以从**时间信息**反推出
  "这一夜有没有技能位"。这是场外信息泄漏。
- **依据**：官方规则本身就在做这件事。百科《规则概要》二-2 要求：
  "当夜晚阶段到达黎明时，简单的等待五到十秒……可以防止玩家们察觉自己可能是在夜晚最后一个行动的玩家。"
  本决策把这条特例**一般化**。
- **选择**：把「节奏」提升为**步骤机的一等职责**，而不是 UI 的动画时长：

  1. **步骤表按剧本展开，不按在场角色展开。** 夜晚的步骤序列来自该剧本的**完整夜晚顺序表**；
     角色不在场 / 已死亡 / 被跳过 → 生成一个**空槽位**，**照样消耗配额**。
     于是"今晚有几个技能位"在时间上**不可观测**。
  2. **每个槽位有固定时间配额**，由服务端节拍器统一驱动；总时长与"实际有多少角色行动"**解耦**。
  3. **黎明等待纳入同一节奏**——百科要求的 5–10 秒是这条规则的一个特例，不是独立规则。
  4. **作废与代填不得缩短夜晚**：请求被作废、被说书人代填、玩家秒回，
     都必须把该槽位剩余配额走完，否则时长立刻变成可观测信号。
  5. **玩家端在夜晚只显示统一界面**：不显示"当前轮到谁""还有几步""进度条""谁正在思考"。
     操作请求**单播**给当事玩家；其他玩家的设备**不产生任何活动指示**。
  6. 抖动只允许由**服务端**注入且对所有人一致；**禁止客户端各自计时**（那会重新引入可观测差异）。

- **代价**：
  - 夜晚被固定节奏拉长：即使所有技能位都空，也要等完整配额走完，短局会变慢。
    这是**用时间换公平**的明账，需求方已明确接受。
  - 槽位配额是"每步**最短**时间"，不是总时长上限：玩家响应慢仍会拉长夜晚（D-0011 无超时）。
    这**不泄漏角色在场信息**（慢的是"某个玩家"，不是"某个角色"），但登记为已知边界。
- **可测性**（不可测的防泄漏等于没做）：
  构造两个夜晚——「全部夜间角色死亡」与「全部夜间角色存活」——记录两条**客户端可观测时间线**，
  必须**观察不到可区分的差异**。验收行见
  `docs/backlog/done/operation-request-step-machine.md`。

## D-0014 自动步骤是建议，说书人可随时接管（兜底与恢复）

- **状态**：Accepted
- **背景**：需求方补充——自动步骤系统是**推荐**而不是强制，说书人必须能"自己调板子"：
  程序逻辑出错时能兜底，房间数据异常时能恢复。
- **选择**：把自动化定位为**建议 + 默认执行**，并给说书人四个一等能力：

  1. **覆盖原语**：强推当前槽位（跳过剩余配额、按原因了结挂起请求）、强制作废、代填；
     在"玩家卡住 / 逻辑出错 / 无合法选项阻塞"时**都必须可用**——兜底入口永远开着。
  2. **接管模式**：说书人可 `TakeOver` 暂停自动节拍、手动逐步驱动，再 `Release` 交还自动化；
     控制模式进事件流，可重放。
  3. **恢复**：房间数据异常时按事件日志重建状态、校验并替换；重建失败**显式报错、拒绝静默继续**。
  4. **审计**：每次接管 / 强推 / 作废 / 代填都记录"谁、为什么、当时状态"。

- **与 D-0013 的边界**：D-0013 的"作废与代填不得缩短夜晚"约束的是**自动行为**；
  强推与接管是蓄意的人工兜底，允许改变节奏，属记录在案的例外，不是系统性时序泄漏。
- **与 D-0010 的边界**：回退到任意序号（截断重放）不在本决策范围内，属后续能力。
- **影响面**：步骤机状态（控制模式）、说书人命令面、宿主节拍器（接管时暂停）、恢复服务、审计事件。

## D-0015 状态账边界：记录事实与归因，不替结算引擎推导维度

- **状态**：Accepted
- **背景**：说书人上帝视角（每一步"为什么是这样"）与后续结算引擎都需要"当前态"。
  事件流里只有"变化"（`SeatStateChangedEvent`）和"效果"（施加 / 终止），没有"完整状态"。
- **选项**：
  - A. 状态账只把**已观测事实**与**效果归因**折起来：维度怎么变由写入方产出事件决定；
    效果的施加、作用对象、终止原因单独成账。
  - B. 状态账按当前生效的效果**自动推导**维度（投毒者的效果一生效就自动把目标标成中毒，
    效果一终止就自动改回健康）。
- **选择**：**A**。
- **代价**：来源死亡后，账本只会说"这条投毒效果已终止"，**不会**顺手把目标的中毒改回健康——
  解除必须由结算引擎（引擎落地前由说书人上报兜底；现由 `DimensionEffectReconciler` 承担）
  产出一条新的状态变化事件。
  多写一条事件，换来的是：平台不臆造事实（D-0002）、六维度各只有一个写入方、
  重放结果不依赖"推导规则怎么实现"。
- **推论**：结算引擎落地时必须实现两件事（2026-10-02 已实现，见
  `docs/backlog/done/settlement-engine.md`）——
  1. "按仍生效的效果重算目标维度并产出变化事件"（账本只报告效果终止，不替它翻转维度）；
  2. 施加效果时一并给出**施加时的来源角色**（`PersistentEffect.SourceCharacter`），
     否则"来源换角色即失去原能力"（二-7）无从判定。
  在那之前 `GameState.OperativeEffectsOn` 与效果终止原因就是它现成的输入。

## D-0016 语言策略修订：全中文，不强制英文

- **状态**：Accepted（取代 D-0006 的语言条款）
- **背景**：D-0006 沿用参考项目 CUO 的"代码全英文"约定，但落地后代码库实际是

- **选项**：

## D-0017 开局分配的载体：事件流，不是会话票据

- **状态**：Accepted
- **背景**：结算引擎的第一件事是建表（`NightPlanBuilder`）：它需要"哪一席是什么角色"。
  此前 `GameSetup` 只有票据，没有任何载体能表达角色分配；而角色是六维度之一，
  状态账（`GameState`）本来就为它留了账位。
- **选项**：
  - A. 扩展 `GameSetup`（会话记录）：随票据持久化、改动小；但游戏状态进了"会话信息"，
    撤销 / 回放 / 投影都覆盖不到，还会与状态账形成第二个来源。
  - B. 新命令 + 事件：`AssignCharactersCommand` 产出每席一条 `SeatStateChangedEvent`
    （角色 + 初始生死），折进 `GameState`；说书人 / 宿主执行，走四道闸。
  - C. 复用 `ApplySeatStateCommand` 逐席上报：零新事件，但缺"开局分配"的原子性与完整性，
    建表无法区分"不在场"与"忘了分配"。
- **选择**：**B**。
- **代价**：
  1. 需要在**阶段开始之前**就能写事件：步骤机重放必须容忍账事件先于任何 `PhaseStartedEvent`
     （`StepMachine.Apply` / `Fold` 已按此调整），`GameSession` 增加一条预阶段提交路径；
  2. 分配与初始生死在同一条事件里记录（R-0015），必须写明"这是补全初始条件、
     不是运行期把两个维度耦合"。
- **推论**：建表所需的一切输入都有唯一来源——角色 / 生死来自事件流（本决策），
  席位名单来自服务端持有的会话信息（客户端声明不可信，D-0012），
  口径来自命令参数并记录在计划上（R-0014）。

## D-0019 说书人注记的状态层级：本局级、进事件流、独立注记账

- **状态**：Accepted（2026-10-03）
- **背景**：官方魔典允许说书人在席位旁挂**自由文本**提示标记（示例：「18 不共边」）。
  平台此前只做**由事实派生**的提示标记；自由文本不是游戏状态事实，直接折进状态账会违反 D-0015。
  票据 `docs/backlog/todo/storyteller-annotation.md` 开工前必须回答四件事：归属 / 持久化 / 边界 / 呈现。
- **选项**（归属与持久化一起决定；三项在玩家侧口径一致：**零下发**）：
  - A. **本局级 + 进事件流**：增 / 改 / 删各一条说书人专属事件，折叠成独立注记账——
    重启 / 重连 / 换设备都在、多台说书人设备一致、可审计可重放；撤销 = 截断重放时一并回退；
  - B. **本局级 + 旁路存储**：单独一张房间级表，不进事件流——重启 / 重连仍在，
    但没有重放 / 撤销语义，等于给同一房间开第二条历史与同步路径（与 D-0010 分叉）；
  - C. **说书人本机便签**（`localStorage`）：零服务端改动，但只属于这台浏览器，
    换设备 / 清缓存即丢、多设备不一致，也不随本局数据走。
- **选择**：**A**（需求方 2026-10-03 拍板）。
- **理由**：D-0010 已经定死「事件是唯一事实来源」；注记属于这一局的局面信息（官方示例就是
  挂在席位旁的魔典标记，不是浏览器便签），必须与局面同生命周期、同恢复路径。
  选 A 后「重连 / 重启 / 撤销 / 多设备一致」四件事全部由既有机制免费得到，没有第二条历史。
- **边界（不可协商的部分）**：
  1. 注记**不参与任何规则判定**，不进 `GameState`、不进 `NightPlanBuilder` 的任何输入；
  2. 玩家投影里**根本不下发**（D-0012 §4.3）：没有玩家端入口、没有推送、没有字段；
  3. 增删改都是事件，不物理删除历史（审计留在事件流里，与 D-0014 的记录纪律一致）；
  4. 呈现走说书人视图的序号流：Join / 推送 / 重连补齐与既有视图同一份事实（D-0010）。
- **代价**：
  1. 事件流里出现一类**非规则事实**的事件；因此它在折叠上必须是**独立注记账**，
     而不是往状态账里塞字段——否则 D-0015 的边界会被磨掉；
  2. 文本要有界：服务端归一化 + 长度上限（120 字符）+ 每席条数上限（5 条），
     前端仍按不可信输入做二次有界化（架构 §4.4）；
  3. 撤销截断会把注记一并回退——这是"本局历史"语义的必然结果，不做特例。
- **推论**：将来若要"给玩家看某条提示"，走已有的「信息结果」能力（按收件人投影），
  不扩本决策；注记永远只说书人可见。

## D-0020 自动化复盘：事件流的呈现投影 + 两张可见面

- **状态**：Accepted（2026-10-04）
- **背景**：票据 `replay-auto-review` 要求「在圆盘上逐步回放每一个原子步骤」。开工前有三件事要一并定稿：
  复盘与事件流的关系、时间轴的步骤粒度、玩家面与说书人面怎么分（票据明确要求「开工时一并确认」）。
- **选项**：

  2. **步骤目录显式登记**：每个 `GameEvent` 类型必须被某个 presenter 认领，或在**显式排除清单**里（附规则引用）；

  4. **性能**：按事件序号分页 + 客户端窗口化渲染；播放节拍是呈现态，与 D-0013 的对局配额无关。
  5. **呈现复用**：圆盘 / 席位牌 / 标记与实时魔典同一套术语与组件口径（票据矩阵行 9）；新增标记先登记
     `docs/standard/terminology.md` 再落代码。
- **代价**：
  1. 文案 / 标记 / 盘面增量要按事件类型逐个登记（首版 50 类事件），是显式成本；换来的是顺序保真可测、覆盖面不会静默退化。
  2. 玩家在终局后能看到全量事实（含裁量与真假信息）——这是「终局揭示」的刻意选择（R-0043），不是投影放松；进行中仍零泄露。
  3. 前端出现一个**终局后可见**的新契约类别与 `features/replay` 依赖：D-0018 的玩家侧门禁需要**显式登记**扩展
     （新类别 + 允许清单），禁止绕过。

## D-0021 账号与玩家名：三层身份、席位认领与会话级承载

- **状态**：Accepted（2026-10-04，E30 开工定稿）
- **背景**：票据 `account-and-display-name` 要解决"局内每个人知道对面是谁"。需求方定稿：
  **M1 局内玩家名与 M2 账号系统一起做，玩家名以账号为准**。开工前必须回答的五件事
  （承载层级 / 来源与权限 / 唯一性与冒用 / M2 边界 / 术语）在此一并定稿。
- **选项**（承载层级，其余四问围绕它展开）：
  - A. **会话级**：席位绑定与玩家名是**会话信息**（服务端持有的 `SeatBindings` 表 + 会话读模型），
    不进事件流、不进 `GameState`；账号是全局身份（`Users` 表），玩家名是账号属性。
  - B. **事件流级**：席位认领与改名写成本局事件，随 D-0010 重放；账号仍要一张全局表存口令。
  - C. **无账号**：每个席位自填一个自由文本姓名（票据 M1 的原形态），不建账号系统。
- **选择**：**A**（C 被需求方否决：M2 纳入首版）。
- **关键口径**：
  1. **三层身份并存**（D-0012 的展开）：账号解决"你是谁"（跨局、持久）；会话票据解决
     "你在这一局是谁"（服务端生成、线下分发，语义不变）；连接凭据解决"这条连接是谁"（不变）。
     三者不得互相取代——账号不直接开任何游戏权限，票据也不再单独决定"显示成谁"。
  2. **席位入口 = 票据认领**：登录后凭本局席位票据加入即绑定（一席一账号、一账号一席）；
     认领后重连可**只带账号**（服务端按绑定解出席位），票据路径照常可用。
     **保留"仅票据"的游客路径**：游客席位没有玩家名，界面一律回退「N 号」（票据矩阵行 6）。
  3. **玩家名是账号属性**：注册时设定登录名（唯一、大小写不敏感）与玩家名（有界化：长度 / 字符 /
     空白折叠）；玩家名在账号设置里随时可改、**即时生效**（改名推送全桌与说书人视图）。
     不做"开局锁定"——姓名不参与任何判定，锁定只会制造麻烦。
  4. **允许重名**：服务端不做唯一性判定、不做阻塞；姓名是标签不是凭据，席位号始终与玩家名同屏。
  5. **找回 = 一次性恢复码**：注册时发放（只显示一次、服务端只存哈希），用它重置口令并作废旧会话；
     不做邮箱、第三方登录与管理后台（D-0005 的依据）。
  6. **秘密姿态**：口令 PBKDF2（随机盐 + 迭代 + 固定时间比较）；账号会话 token 密码学随机、
     **只存哈希、内存、有 TTL、可撤销**；口令与 token 都不进日志、不落盘、不进前端持久化。
  7. **不进四道闸**：账号自助（注册 / 登录 / 改名 / 找回）不是游戏命令，只改账号与会话数据；
     身份的最终判据仍由服务端持有的凭据与绑定推导（D-0012"客户端声明一律不认"不变）。
- **代价**：
  1. 新增口令 / 会话 / 找回三条攻击面：负向测试与门禁（`CredentialSecurityGateTests` 扩展）
     是本决策的交付物，不是可选项。
  2. 姓名不参与判定 ⇒ **无法防冒名**（无唯一性、无账号之外的校验）；这是刻意取舍——
     票据与连接凭据才是身份，姓名只负责"看得懂"。
  3. 旧库不兼容：新增 `Users` / `SeatBindings` 表，而现库用 `EnsureCreated`、不会给已有库补表；
     启动时探测缺表**显式失败并提示换新库**（不做在线迁移、不静默继续）。
  4. 事件流里没有姓名历史：复盘的"谁"显示的是**读取时**的账号玩家名；将来若要求
     "第 N 步时叫什么"的逐步骤历史，需要把绑定 / 改名升级为事件——那是另一票，不在本决策内。
  5. 游客席位没有玩家名，"回退 N 号"因此是长期活路径，不是过渡态。
- **与既有决策的边界**：D-0010 / D-0019 的"事件是唯一事实来源"限定在**游戏事实**范围内不变
  （角色 / 生死 / 注记等仍进事件流）；姓名与席位绑定是**会话事实**，与席位名单、票据同类
  （D-0017 推论），因此不进事件流。D-0012 的票据"只定位、不授权"语义不变。

## D-0022 首版纳入旅行者与流放流程

- **状态**：Accepted（需求方 2026-10-04 确认）
- **背景**：D-0003 把首版剧本定为《梦殒春宵》全集；剧本页列有 5 名旅行者
  （怪咖 / 集骨者 / 咖啡师 / 流莺 / 屠夫）。此前该范围挂在 `rulings.md` R-0007（Open）与本文件
  「待决事项 P-1」。需求方 2026-10-04 明确：**旅行者与流放流程纳入 MVP**。
- **选择**：**纳入首版**。范围 = 剧本自带的 5 名旅行者 + 流放流程 + 加入 / 离开流程。
- **关键口径（已确证部分）**（来源：百科《旅行者》《重要细节》一-4，抓取日期见票据）：
  1. 旅行者可在游戏任意时刻加入：玩家自选角色、说书人私下给定阵营；邪恶旅行者得知一名存活恶魔、
     不告知爪牙；加入时向其他玩家宣告「谁 + 什么角色 + 能力」，但不公布阵营；
  2. 与普通角色相同的面：可提名 / 投票、夜晚行动、被恶魔杀死、醉酒 / 中毒失效、死亡得投票标记；
  3. 与普通角色的差异：**不计入「仅有两名玩家存活」的邪恶获胜条件**；只能通过**流放**死亡；
  4. 流放：白天任意时刻任意玩家（含死者）可发起；不计入提名次数；全员表决（含死者、
     死者不消耗投票标记）；**任何角色能力不能影响流放**（R-0007 引《重要细节》一-4）；
     支持票达到**全体玩家**一半即成功；同日可流放任意多名；每名旅行者每天仅可被提议一次；
     流放不影响当天处决；
  5. 旅行者↔非旅行者转换默认禁止（说书人摇头示意另选）；允许转换属房规，平台不做。
- **代价**：
  1. 首版范围扩大：5 个角色 + 一条全新的白天流程（流放）+ 加入 / 离开流程；
     `MalfunctionKind.Barista`（R-0004）由「预留」转为「可用」，其口径要跟着核对；
  2. 流放与提名 / 投票 / 处决 / 投票标记 / 投影 / 复盘交互面广，必须整套走（不许只做界面）；
  3. R-0007 原先「若不纳入要显式声明」的分支作废；**实现前界面不得声称支持旅行者**（现状仍不支持）。
- **边界（明确不做）**：实验性旅行者（黑帮 / 笑匠 / 侏儒等）；旅行者↔非旅行者转换。
- **落地承接**：`docs/backlog/todo/traveller-and-exile.md`（Todo；细则清点、验收矩阵与来源补抓在票据里）。
