# 代理工作细则

> 上级约束在 `AGENTS.md`；本页是它的执行细节。**本页只讲怎么做，不重复规则本身。**

## 1. 门禁怎么跑

```bash
dotnet build OpenClockTower.slnx
dotnet test  OpenClockTower.slnx
dotnet format OpenClockTower.slnx
```

- 三者全绿才提交。纯文档改动（未触碰 `src/ tests/ tools/ web/`）跳过三者。
- **验证期间不要并行改代码或重建产物。** 构建产物被重写时跑出来的红/绿都不可信：
  先冻结被验证的工作树，再验证。
- 出现"红了几次又莫名其妙好了"时，先查有没有并发构建或残留进程在写同一产物，
  再按**可重复性**判定；原因未定之前不要急着改产品代码，也不要宣称已修复。

## 2. 提交

- Conventional Commits：`type(scope): summary`，类型限
  `feat fix docs test chore refactor perf revert build ci style`。
- scope 用短的领域或路径名（`kernel`、`rules`、`docs`、`web`）。
- 摘要用祈使句，前缀后全小写（专有名词保留大小写），无句尾句号，单行。
- GPG 签名已全局开启，直接 `git commit`；**不要**定位 gpg、不要
  `--no-gpg-sign` / `-c commit.gpgsign=false` / `--no-verify`。
  签名需要人工输密码时会挂起等待——这是**正常等待**，不是故障，不要中断它。

## 3. 收尾清场（自己的产物自己清）

工作过程中创建的临时目录、日志、调试产物、备份、一次性脚本，**收尾时必须自己删掉**。

- 判断标准两个问题：**这东西是我产生的吗？它的用途结束了吗？** 两个都是"是"，就删。
- 保留下来的只有三种情况：(a) 进程/会话正在占用它；(b) 需求方明确说别动；(c) 它是交付物。
- **删除纪律（红线）**：禁止任何形式的递归删除（`rm -rf`、`Remove-Item -Recurse` 等）。
  每一步删除分三步走且不可合并：**查看目录 → 单层批量删除 → 回看目录**。
  嵌套目录逐层重复三步。范围不确定的目录改用回收站或改名加 `.trash-<日期>` 交给需求方。
- **总结里必须写清**：清了什么（数量与位置）、还剩什么、为什么剩。

## 4. 检索纪律

- 禁止全盘/无界搜索（`find /`、对盘符根递归列目录、对用户主目录递归扫描）。
- 动手前先说清"在哪棵子树里找"，用 `glob` / `grep` 这类自带范围与条数上限的工具。
- 必须用 shell 递归时，同一条命令里同时给出超时、条数上限与深度上限。
- 派发子代理时，把这段规则写进子代理的提示词里。

## 5. 独立对抗性自检

提交**之前**跑，不是之后。要求：

- 在**新的上下文**里跑（子代理），不要用写完代码的同一个上下文自己复核自己；
- 针对**冻结的工作树**（自检期间不改代码）；
- 结论按严重度列出，**本轮修掉**；确实修不完的记入 backlog 并写明原因。

自检重点问这几个问题：
1. 这条链路在**运行时**怎么被证明的？
2. 我是不是只修了被报告的那一个点，同族还有没有同病？
3. 有没有把"角色/阵营/生死/醉酒/中毒"耦合起来？
4. 信息隔离的反方向（不该看见的人）验过没有？
5. 我有没有偷偷把一个没验证的东西说成已验证？

## 6. 交接提示词

每个工作项收口时必须产出，**在同一回合**输出。结构：

```text
1. 工作区复核   仓库 / 分支 / HEAD / git status 结论
2. 本轮已落地   做了哪些改动，附证据与提交号
3. 已知缺陷     未验证与已知缺口，按严重度排序
4. 下一步建议   做什么、为什么是它
5. 门禁与流程   本轮跑过什么、有什么需要注意的
6. 收尾清场     清了什么、还剩什么、为什么剩
```

触发信号（出现任一即必须输出，不等需求方开口）：
本轮目标完成 · 门禁全绿且工作树干净 · 票据已移动 · 下一个动作属于另一个工作项 ·
本轮已产生 1 个以上提交 · 上下文开始紧张。

## 7. 上下文与并行

- 大范围、读大量资料的子任务（如规则核对、整族审查）**推给子代理**，
  它在自己的上下文里收束，主线的注意力留在关键路径上。
- 需要等子代理结果时：有 goal 先 `pause`，然后**结束本回合等推送**。
  禁止任何形式的阻塞等待（`sleep`、轮询、反复 `ls` 看文件出现没有）。
- 上下文接近耗尽时，在阶段边界停下交接，不要在耗尽的上下文里硬写。

## 8. 装置与工具陷阱

- **`tools/verify-*.mjs` 的 `waitUntil(condition, timeoutMs)` 只接受同步谓词。**
  谓词返回 Promise 时助手**直接抛错**：助手不 await 谓词，Promise 恒真会让第一次检查立刻通过——
  断言假绿、红绿看运气。要等异步条件就自己写轮询，或改用 `locator.waitFor` /
  `waitForAttribute` / `waitForLocatorContains`。
- **截图要拍在被断言的那一步**：先截图、再点「下一步」做后续观测。E29 实测：`cc-17` 曾把「换角」
  的截图落在标记的下一步（自死步）——修正为标记步本身 + 自死步另存 `cc-21`。截图复核要对着断言文案
  核对内容，不是只看文件存在。
- 装置报告红时，先分辨是**产品缺陷**还是**夹具节拍假设**：迭代档下靠近节拍窗口的断言会时有时无，
  先看 `--quota` 与分段重跑，再下结论（口径见 `AGENTS.local.md`「验证成本纪律」）。
- **窄窗口 ≠ 夹具噪声**：能把时序前置（如把"应答"延后到配额到点之后）就变成**确定性复现**的，是产品缺陷——
  先写确定性复现，再改代码。实例：配额输入幂等键按「计划 + 槽位」→ 改为按「每次进入」
  （见 `backlog/done/sage-and-sweetheart.md`「残余补证」）。
