# 验证与证据

> 本页回答：**什么样的一段文字才配叫"证据"，以及它存在哪。**
> 一句话原则：**纸面审查 = 没审查。** 每条关键链路都要能回答"它在运行时怎么被证明？"

## 1. 什么算证据

| 算 | 不算 |
|---|---|
| 一次真实构建的输出（含 error/warning 计数） | "应该能编译通过" |
| 一次真实测试运行的输出 | "测试覆盖了这个逻辑" |
| 一次真实对局会话的记录（谁在第几步做了什么、状态怎么变） | "按代码看会这样" |
| 本次运行拍下的界面截图 | 上一轮的旧截图 |
| 抓取到的百科正文 + 它的 SHA256 | 记忆里的规则 |
| 日志中带上下文的行（分支、状态、玩家 id、输入、结果） | 一行"出错了" |

## 2. 证据放哪

| 类型 | 位置 | 提交进仓库 |
|---|---|---|
| 门禁与测试输出 | 提交信息正文 / 票据的「证据」列 | 是（文字摘要） |
| 长日志、抓包、截图 | `artifacts/`（gitignored） | 否，只提交摘要 |
| 百科正文快照 | `references/wiki/`（gitignored） | 否，只提交 `references/wiki-index.json` |
| 百科引用 | 写成 `页名 + 抓取日期 + 区域` | 是 |
| 验收结论 | 票据内「验收矩阵」的证据列 | 是 |

## 3. 先红后绿

**修复缺陷、加门禁、加不变量检查时，必须先让期望的失败出现一次。**

- 加了门禁但从未见它红过 → 不知道它到底在不在工作，等于没加；
- 记录格式：`先红：<命令> → <失败输出摘要>` / `后绿：<命令> → 通过`。

这不适用于新功能（新功能没有"期望的失败"），但适用于**任何守规则的机制**。

## 4. 日志

- 关键路径与每个逻辑分支都要有日志；
- 按触发频率选级别：高频 `Debug/Verbose`，低频或异常 `Warn/Error`；
- 必须带定位上下文：分支名、状态、玩家/角色 id、输入、结果；
- 标准是"出问题后不需要再来一轮'改代码→部署→复现→补日志'"。

## 5. 引用我们自己的代码

引用 `src/ tests/ tools/ web/` 时：**写路径 + 引文，不写行号**——行号会漂。
引用 `references/wiki/` 时可以带行号（那棵树不被编辑）。

## 6. 什么时候不能用测试顶替验证

以下这些**只能靠一次真实运行**，单元测试再绿也不算：

- 断线重连后两端状态一致；
- 玩家端**确实没收到**不该收到的信息（信息隔离方向）；
- 多客户端并发操作下的序号单调与幂等；
- 界面上说书人真的能找到那个裁定入口；
- **传输面加固是不是真的生效**（响应头 / 请求体与连接上限 / 反代层的限流与真实 IP）：
  集成用例跑的是 TestServer 的内存连接，拿不到"哪一层拒的""反代有没有把它自己的那份头发出来"
  这类读数——必须用 `tools/verify-transport-hardening.mjs` 打一次真协议栈（本机直跑宿主，或部署实例）。
