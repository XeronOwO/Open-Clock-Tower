# 裁定登记表（Ruling Register）

> 本表是本项目的**一等交付物**，不是附录。
> 规则里凡是「查不到、拿不准、百科自相矛盾、需要项目自定」的，都必须在这里有一条记录。
> **禁止**把不确定的行为直接写进代码然后当它不存在。

## 为什么必须有这张表

《血染钟楼》的规则由三部分构成：**印刷规则书** + **钟楼百科的角色详解** + **说书人的现场裁定**。
前两者都无法覆盖全部组合（百科自己就写了"三角色相克短期不会整理"），
于是大量行为只能落到"项目怎么算"。这些"项目算"如果散落在代码里，
后人读到就只有默认行为、看不到它其实是**一个未经确证的选择**——这正是本项目要根除的事故源。

## 状态定义

| 状态 | 含义 | 代码侧义务 |
|---|---|---|
| `Open` | 有疑问，尚无可靠依据 | 默认行为处必须写注释引用裁定号；禁止静默生效 |
| `Decided` | 已有依据（百科原文 / 官方设计师回复 / 用户明确决定） | 依据必须可复核（页名 + 抓取日期） |
| `Contested` | 多处依据互相冲突 | 记录冲突双方，暂取其一并说明；对局前须告知玩家实际口径 |
| `Deferred` | 本项目暂不实现 | 必须同时在 UI/文档显式声明"本版本不支持"，禁止静默缺失 |
| `OutOfScope` | 明确不做 | 记录原因与解除条件 |

### R-0002 · 三角色相克如何处理

- **状态**：Decided（2026-10-04 需求方拍板：平台策略定案；百科整理三角色规则时复核）
- **问题**：三个角色互相构成相克时如何裁定，例如「麻脸巫婆把一名邪恶玩家变成哲学家，该哲学家又选择获得异端分子的能力」。
- **依据**：百科《相克规则》原文——"三角色问题会比双角色问题更加复杂，需要考虑的东西更多"，因此
  "在短期内（话先不说死）不会整理'三角色相克'规则"；百科只给了一条类比范例。
- **处理**：
  1. MVP 的相克解析器**只判定双角色相克**。
  2. 遇到三角色及以上组合时，解析器必须返回「未登记」这一**显式结果**，交给说书人现场裁定。
  3. 引擎**禁止自行类推**；裁定完成后追加一条本表条目，并把它变成可回归的测试用例。
  4. 首版触发面（2026-10-04 核对）：纯 S&V 对局**不会触发**相克判定——39 条涉及 S&V 25 角色的
     相克条目，对手均来自其他剧本 / 实验性角色 / 社区剧本（`character-rules.md` §相克条目汇总）；
     5 名 S&V 旅行者（怪咖 / 集骨者 / 咖啡师 / 流莺 / 屠夫）在《相克规则》快照中 **0 命中**。
     本条的真实触发面要等跨剧本扩展（`backlog/future/cross-script-extension.md`）。
- **2026-10-04 核对（实现现状）**：首版代码中**没有相克解析器**——第 4 条的零触发面意味着它暂时没有
  实现载体；`MalfunctionKind.Jinx` 只是失效账本的一个分类，不代表解析器已实现。解析器（含三角色的
  「未登记」显式返回）随 `docs/backlog/future/cross-script-extension.md` 开工。
- **2026-10-04 定案（需求方决定）**：平台策略（只判双角色 + 三角色及以上显式「未登记」+ 禁止类推）
  **定案**，状态由 `Open` 转 `Decided`。实现与回归随跨剧本扩展票落地（首版零触发面、无实现载体）；
  百科整理三角色相克规则后按维护规则回来复核。
- **影响面**：`Rules` 层相克解析器的返回类型必须能表达"未知"，不能只有"冲突/不冲突"两态。

### R-0003 · 疯狂是否可由引擎自动判定

- **状态**：Decided
- **问题**：「疯狂」要不要建成内核里的一个状态位，由引擎判断玩家是否"疯狂地证明了某件事"？
- **依据**：百科《重要细节》三-4 明确——疯狂"更像是一个现实中的状态。你无法在魔典中查看一名角色是否疯狂"，
  且"你作为说书人，有对玩家的表现是否符合'疯狂'状态的最终裁决权"。
- **处理**：
  1. 疯狂**不建为引擎状态**，玩家状态仍只有 角色/阵营/生死/醉酒/中毒 五项可在魔典中观测，
     另加一项**仅由裁定写入**的 `MadnessRequirement`（谁、在何时、被要求疯狂证明什么）。
  2. 引擎负责：产生要求、计时提醒、承接说书人裁定（成立/不成立）、按裁定触发后果（如处决）。
  3. 引擎**不负责**判断玩家发言是否满足疯狂。
- **影响面**：内核领域模型；洗脑师、畸形秀演员、哥布林等角色的实现；说书人端交互。
- **2026-10-03 补充（R-0021）**：本条说的是「是否疯狂」由说书人裁定、引擎不建疯狂状态位；
  要求的**产生方是能力**（洗脑师夜晚行动生效时写入），存续与撤下见 R-0021，处罚后果见 R-0020。

### R-0004 · 「能力未正常生效」的计数口径（数学家）

- **状态**：Decided（咖啡师 / 说书人裁定两条路径仍待核对，见下表）
- **问题**：数学家得知"有多少能力未正常生效"。哪些情形计入、哪些不计入？同一名玩家命中多条路径时怎么算？
- **依据**：百科《数学家》· 2026-10-01 抓取 · 角色能力 / 角色简介 / 运作方式 / 提示标记 / 范例；
  《相克规则》· 开头；《占卜师》· 规则细节；《涡流》· 角色简介；《获取信息》· 错误信息的格式（第 3 条）；
  《重要细节》· 三-3；《更换选择目标》· 与数学家的交互；《梦殒春宵》· 夜晚顺序表。

**计数口径**：

1. **计玩家，不计次数**：《数学家》角色简介——"数学家不会得知异常发生在哪名玩家身上，只会得知异常在多少名玩家身上发生了"；
   同页提示标记——"同一个玩家不论当天能力有多少次未正常生效……均只会在一名玩家的角色标记旁最多放置1枚"。
   《更换选择目标》同义："只看有几名玩家的角色能力未正常生效，而不看一名玩家的角色能力有多少次未正常生效"。
2. **窗口**：从上一个黎明到数学家被唤醒（《数学家》角色能力；《梦殒春宵》夜晚顺序表同义）。
   窗口内换过角色、换过能力，也只计 1（同页提示标记）。
3. **数学家自身不计**："数学家的能力不会检测数学家自身是否未正常生效"（同页角色简介）。
4. **记录与数学家是否在场无关**：剧本里有数学家（含中途被创造 / 获取能力）就应持续记录（同页提示标记）。

**逐条 `MalfunctionKind` 对表**：

| 路径 | 分类 | 计入？ | 依据 |
|---|---|---|---|
| 中毒使能力没按预期发挥作用 | `Poisoned` | 计入 | 《数学家》角色简介：检测"因为中毒……而没有按照预期发挥作用的能力" |
| 醉酒使能力没按预期发挥作用 | `Drunk` | 计入 | 同上 |
| 同一玩家同时中毒且醉酒 | `Poisoned` + `Drunk` 两条记录；该玩家只算 1 | 计入 | 《重要细节》三-3："醉酒与中毒状态不会互相抵消"，两者各自都让能力失去 |
| 涡流存活：镇民通过能力获取的信息必假 | `Vortox` | 计入 | 《数学家》角色简介"本应正确，实则错误的信息"；同页范例：五名善良玩家得到错误信息 + 醉酒女巫 = 六名玩家的能力未正常生效；《涡流》角色简介"哪怕他们醉酒或中毒，信息也一定是错误的"；《获取信息》第 3 条 |
| 相克规则导致能力未正常生效 | `Jinx` | **不计入** | 《相克规则》开头："所有因相克规则而导致自己能力未正常生效的，不会计入到数学家的能力检测中" |
| 能力自身设定的正常结果（占卜师选中"干扰项"得知"是"） | `AbilityDesign` | **不计入** | 《占卜师》规则细节："因为这是他自身能力让自己获取的信息出错" |
| 咖啡师（旅行者）造成的干扰 | `Barista` | **不计入**（2026-10-04 补抓《咖啡师》页收口）：两种效果——① 解除并免疫醉酒中毒 + 保证正确信息；② 能力生效两次——都是让能力**更有效**，不产生「未正常生效」；引擎不写此类失效记录（枚举去留与免疫期间的中毒账本口径见旅行者票据） | 百科《咖啡师》· 2026-10-04 抓取 · 角色能力 / 角色简介 / 运作方式 / 规则细节 |
| 说书人裁定 | `StorytellerRuling` | **待核对**——当前没有实现路径；用到时先补本表（2026-10-04 复核：仍无实现路径） | — |

**组合与并存**：一次结算可以同时命中多条路径——失效账本**逐条记录、互不顶替**（不硬塞成单分类、也不互相抵消）；
对数学家的数字仍按第 1 条只算该玩家一次。

**平台边界**：平台不判信息真假（D-0002 / R-0028）。信息类能力在中毒 / 醉酒下"信息可能错也可能对"
（《重要细节》三-3；《占卜师》要求确实与正常结果不同才计入），账本记的是"来源处于该状态且能力已结算"这一机制事实，
最终数字由说书人给出（《数学家》运作方式：说书人比划数字）；涡流在场时信息必须为假（R-0028），`Vortox` 记录是确定事实。

- **2026-10-03 补充（首夜窗口，批次 E21）**：首夜不存在「上一个黎明」，窗口下界取**本局开局**——
  首夜唤醒前已记录的失效都计入（含首夜更早槽位）。依据：角色能力原文「从上个黎明到你被唤醒时」
  （百科《数学家》· 2026-10-01 抓取 · 角色能力）；首夜唤醒见《夜晚行动顺序一览》· 2026-10-01 抓取 ·
  首个夜晚段（数学家条）。该页无首夜专条，本条为平台登记口径。实现：失效账本黎明水位
  （`MalfunctionLedger.SinceDawnStart`，`DayStartedEvent` 折叠时推进；首夜为 0 = 全账）。

- **影响面**：内核失效账本（多原因列表 + 按玩家去重 + 黎明水位）与 `AbilityEffectivenessEvaluator`；
  全部信息类角色契约（涡流声明）；数学家角色实现见 `docs/backlog/in-progress/mathematician.md`（批次 E21）。

### R-0005 · 相克规则与「不能最大」的优先序

- **状态**：Decided（2026-10-04 需求方拍板：暂定序为平台口径，遇反例即改）
- **问题**：相克规则是"规则"而不是角色能力（百科明确说明）。当相克规则与角色能力冲突、
  或相克规则与"不能最大"原则冲突时，谁优先？
- **依据**：百科《相克规则》："相克规则是规则而非灯神的能力"；
  百科《钟楼谜团隐性规则汇总》第 2 条"不能最大"：两个能力冲突时以"不能"的一方生效。
- **处理**：实现采用**暂定优先序**：`相克规则 > 不能最大 > 角色能力 > 核心规则`。
  **此序未获百科确证**，属于项目自定口径；一旦出现反例立即改此处并同步改代码。
- **2026-10-04 复核**：《隐性规则汇总》§2 原文为「两个能力（**或规则**）之间互相冲突时……始终以
  '不能'的能力生效」——"不能最大"本身就涵盖规则之间；但「相克规则」与「不能最大」谁先，两页均无
  条文，暂定序维持。另：首版没有通用冲突解析器（无触发场景），该序目前只是登记口径。
- **2026-10-04 补充（印刷规则书正文）**：规则书明确「角色能力打破本规则书的核心规则……冲突时依角色
  能力（唯一例外：能力不能影响旅行者的流放）」，并要求能力之间的冲突按该角色的 almanac（角色详解）
  裁决——"角色能力 > 核心规则"这一层由此获得权威依据；但「相克规则 > 不能最大」仍无条文，
  暂定序的前两层维持项目自定。
- **2026-10-04 补充（官方英文 wiki《Djinn》）**：jinx（相克）由灯神的 **special rule** 承载——
  「The Djinn resolves jinxes by creating a unique rule」，即每一对相克角色有一条规定该组合怎么处理
  的专门规则；这支持「相克规则是特殊规则、优先于常规冲突判定」的定位。
- **2026-10-04 定案（需求方决定）**：暂定序 `相克规则 > 不能最大 > 角色能力 > 核心规则` **定为平台口径**，
  状态由 `Open` 转 `Decided`；首版无通用冲突解析器、零触发面，实现与回归随跨剧本扩展票落地；
  一旦出现反例或官方条文与暂定序冲突，按维护规则改此条并同步实现。
- **影响面**：内核冲突解析器（决定性模块）；说书人端的裁定提示。

### R-0006 · 百科图片热链的可用性

- **状态**：Decided（2026-10-04 实测：无防盗链、`<img>` 无需 CORS；桌面 Chromium + 移动端仿真 + 局域网 origin 探针全过；回归 = 单元 / SSR 测试 + `tools/check-character-art.mjs`）
- **问题**：程序在运行期外链 `clocktower-wiki.gstonegames.com` 的图片，是否会遇到防盗链 / Referer 校验 / 跨域限制？
- **依据**：2026-10-04 首轮实测（见下）。方案由需求方选定（见 `docs/decisions/active.md` D-0007）。
- **实测（2026-10-04）**：
  1. 角色图 25 张逐张：`200` + `image/png`（地址取自 `web/src/display/character-art.ts`；`artifacts/web/wiki-image-probe.log`）；
  2. Referer：带本站 Referer 与不带均 `200`——**无防盗链**；响应无 `Access-Control-Allow-Origin`，
     但 `<img>` 显示不需要 CORS；
  3. 缓存：无 `Cache-Control`，有 `Last-Modified` / `ETag`（浏览器启发式缓存 + 条件请求）；
  4. 浏览器侧探针 A–D 全过（`tools/check-character-art.mjs`）：正常加载 / 阻断主机后撤图降级 /
     未知 slug 不请求 / 局域网 origin（`http://192.168.77.77:5391` 仿真）+ iPhone 13 上下文的加载；
  5. **不做真机手机验证（2026-10-04）**：角色图是公开 HTTPS 静态资源，请求不带 Referer、
     不涉 Cookie / CORS——手机与桌面浏览器之间没有设备侧变量；移动端已由仿真覆盖。真实移动网络
     （运营商代理 / DNS 等）与"换一条网络出口"等价，且图片失败时由降级兜底，不列为前置条件。
- **处理**：
  1. 必须实测（含移动端浏览器与局域网访问两种场景），把结论写回本条目——自动侧已完成（第 4 条），
     真机不作为前置（第 5 条）；
  2. **无论测试结果如何**，前端一律实现图片加载失败降级：显示角色名 + 阵营色块，不留白、不裂图——
     已落地（`CharacterArt.vue` 的 `@error` 撤图；见 D-0007 落地形态）。
- **影响面**：前端角色标记组件；`docs/decisions/active.md` D-0007 的成立与否。

### R-0012 · 来源醉酒 / 中毒时，持续型效果是「终止」还是「挂起」

- **状态**：Decided（2026-10-04 印刷规则书正文确证「挂起」口径）
- **问题**：百科同一段里先说这种效果"会终止"，紧接着又要求"恢复后继续生效"。平台按哪种建模？
- **依据**（2026-10-02 核对 `references/wiki/重要细节.wiki` 快照）：
  - 冲突一方 · 二-3（第 23 行）："角色能力会在死亡，中毒或醉酒的那一刻立即失去，
    **同时能力产生的所有持续型效果也会终止**。"
  - 冲突另一方 · 同段下半句 + 三-3（第 125–130 行）："如果角色从中毒或醉酒中恢复健康和清醒，
    角色能力和**原本已经生效的持续型效果也会继续生效**"；范例：茶艺师中毒 → 不再保护邻近玩家，
    恢复健康 → 再次保护；女巫醉酒 → 诅咒失效，恢复清醒 → 诅咒恢复。
  - 旁证 · 二-4（第 33 行）："这些能力仍然会在玩家醉酒或中毒时**暂时**失去"。
- **处理**：取**挂起**（suspension）：
  1. 来源醉酒 / 中毒 → 效果**不终止**，只是当前不生效（`PersistentEffect.IsOperative` 为 false）；
     来源恢复清醒健康后**继续生效**，且**不是重新施加**（同一个 `EffectId`）。
  2. 只有**来源死亡**（二-3 投毒者范例）或**来源换了角色、失去原角色能力**（二-7）才是不可逆的**终止**。
  3. 二-3 里"终止"一词按"立即失效"理解；与同段后半句及三-3 的范例冲突时，以后者为准。
  4. **终止不可逆，但"重新获得同一能力"是另一回事**：来源复活、或换走之后又换回原角色时，
     角色能力重新生效 → 产生**新的一条效果**（新的 `EffectId`，如 `…:2#2`），
     而不是让已终止的旧效果复活。结算对账按这条规则处理（`SettlementReconciler` 的世代规则）。
  5. **2026-10-04 收口（印刷规则书正文）**：规则书写明「能力在死亡、中毒或醉酒时立即失去」，
     并把死亡时的终止**限定为持续效果**——「若角色死亡，他们立即失去能力，其能力的**持续效果终止**」；
     醉酒 / 中毒时则是「通常**不要移除**提示标记，以防他们恢复清醒健康；在此期间可以忽略它们，
     因为醉酒中毒玩家没有能力，就像死了一样」。→ **死亡 = 终止；醉酒 / 中毒 = 挂起（不撤、可恢复）**，
     与暂取口径一致；百科二-3 的「终止」措辞按同页三-3 理解，不改实现。
     来源：印刷规则书提取文本 · 2026-10-04 抓取 · 「能力与状态」章节
     （本地留档 `references/rulebook/`，索引 `references/rulebook-index.json`；
     第三方逐字提取，官方原件待拿到实物后复核）。
- **代码侧义务**：`PersistentEffect` 与 `GameStateMachine` 的相关注释必须引用本条；
  `EffectAttributionTests` / `EffectLifecycleTests` 的挂起与恢复用例是本条的回归。
- **影响面**：`PersistentEffect.IsOperative`、`GameStateMachine` 的来源失效传播、`GameState.OperativeEffectsOn`、
  后续结算引擎"按仍生效的效果重算维度"。

### R-0017 · 在线白天的钟盘收票与计票语义

- **状态**：Decided（2026-10-04 需求方给出目标形态「钟盘投票」，同日按设计定稿落地并通过验收批次）
- **问题**：线下白天由说书人绕圈逐个点数，"在你指向他的时候举起了手"就是计票时刻；线上没有
  这个物理过程。被提名后什么时候算票、能不能改票、死亡玩家的票什么时候消耗？
- **依据**：百科《投票》《规则概要》只描述线下流程，没有可照搬的在线形态；
  按本表规则属于"查不到 → 必须登记"。需求方 2026-10-04 给出**钟盘形态**目标口径；
  设计定稿、实现与取证见 `docs/backlog/done/clock-vote-flow.md`。
- **处理（现行行为，代码注释必须引用本条）**：
  1. 提名成立后，由说书人点「开始收票」进入**倒计时**（默认 3000ms，可调 1000–10000ms）；
     随后分针按**席位号升序**逐席旋转收票（间隔默认 1000ms，可调 300–5000ms）——
     第 k 席（1 起）在 `开始时刻 + 倒计时 + k × 间隔` 到点。
  2. **严格时点收票**：分针指向某席的那一刻，以该席**已登记的举手状态**为准，固化成一条冻结
     结论——先举也算、过时不候；本席收票后再举手 / 放下被显式拒绝（`day.seat_collected`）。
     不设反应窗口；网络抖动由可调间隔吸收。
  3. **收票全部完成后**才能计票（未收完 → `day.sweep_incomplete` 显式拒绝）；票面 = 逐席冻结
     结论，原三条件（严格最多 / ≥ 存活人数一半 / ≥1）与平局、后来者规则不变；计票后本次提名
     不再接受输入。
  4. 死亡玩家的投票权在计票时消耗——前提是他被计为投票者（与《投票》"只要他举手且票数被成功
     统计，他就会失去投票机会"一致）；举手时票权已用完则拒绝（`day.vote_token_spent`）。
  5. **公开面**：提名、"谁举着手"、当前席位与已收票结论都是**公开信息**——线下说书人绕圈点数时，
     每名玩家举没举手、点到谁、数到几所有人都看得见（百科《规则概要》三-2）。举手 / 已收票 /
     收票相位对**全体玩家**可见；这是线下公开面的渲染等价物，不是新增信息面。
  6. **节奏参数只属呈现**：倒计时 / 间隔随 `VoteSweepStartedEvent` 进事件流（重连 / 重启 / 重建
     能复现节奏），但**判定完全不读**；它们不是会话级持久设置，每次收票由说书人显式提交。
  7. **中断与继续**：服务端重启 / 重建时未完成的收票**不追补**（断线期玩家无法举手），状态为
     「已中断」，由说书人点「继续收票」（`VoteSweepResumedEvent`）重新起倒计时、从下一未收席位
     继续；每席实际收集时刻以事件流存储时间戳如实保留。
- **影响面**：`NominationRecord`（`Ballot` = 已收票冻结、`HandsRaised` = 举手、`Sweep` = 收票
  状态）、`DayMachine`（`StartVoteSweep` / `CollectSeatVote` / `ResumeVoteSweep` / `CastVote` /
  `CountVotes`）、`VoteSweepPacer`（控制面时间轴；时间只在应用层）、`DayViewDto` /
  `DayNominationDto` / `PlayerDayDto`、说书人面板与玩家端钟盘控件；改为"计票后才公开票面"
  "给某席反应窗口"或让参数参与判定，必须先改本条目并同步代码与测试（内核用例
  `VoteSweepMachineTests`、投影用例 `PlayerDayProjection_IsPublicOnlyAndIdenticalAcrossSeats`）。
- **历史口径**：旧形态（投票开放窗口 + 说书人随时快照计票）随本次实现被替换；旧事件类型保留，
  用于旧日志回放（`VoteCastEvent` 在 `Sweep` 为空时仍按旧形态折叠）。

### R-0019 · 女巫诅咒的在线时序与可见面

- **状态**：Decided
- **问题**：女巫的诅咒「下个白天提名即死」在线怎么落？三件事需要项目定口径：
  ①提示标记「被诅咒」谁能看见；②「立即宣布他死亡」在当前架构里对应什么提交形态；
  ③诅咒什么时候撤下。
- **依据**：百科《女巫》· 2026-10-01 抓取 · 角色能力 / 角色简介 / 运作方式 / 提示标记——
  「每个夜晚，你要选择一名玩家：如果他明天白天发起提名，他死亡」；「尽管如此，他的提名仍然生效」；
  「下个白天，如果被标记为『被诅咒』的玩家发起了提名，立即宣布他死亡。（提名正常进行）」；
  提示标记「被诅咒」放置在**魔典上**的角色标记旁，「移除时机：在黄昏时，或女巫死亡或离场时」；
  「只剩三名玩家存活时，女巫的诅咒立即解除」。挂起语义见 R-0012。
- **处理（默认行为，代码注释必须引用本条）**：
  1. **可见面**：诅咒是魔典上的提示标记——只说书人视图可见（效果链 + 牌面标记）；玩家端不含生死账 /
     效果 / 归因字段（D-0012 的投影白名单）。
  2. **时序**：提名与该玩家死亡落在**同一次原子提交**里（`NominationMadeEvent` + 死亡
     `SeatStateChangedEvent`）；提名本身不受影响——票面继续、未计票前白天不能结束。
  3. **撤下**：白天结束（黄昏）时终止；存活降到 ≤3、或女巫死亡 / 换角色时立即终止
     （终止原因分类 `NoLongerApplies` / `SourceDied` / `SourceLostAbility`）。
  4. **死亡的公告面**：本条目只覆盖"事实记录 + 说书人可见"；**玩家端的死亡公告面另立票据**
     （`docs/backlog/done/player-death-announcement.md`），落地时回来补本条目第 5 条。
  5. **死亡公告（2026-10-04 补，见 R-0022）**：被诅咒者死亡属于**公开生死面**——玩家端在白天即时
     看到"谁死了"（提名即死的时点就是公告时点）；诅咒的来源、提示标记与效果仍只说书人可见（D-0012）。
- **影响面**：`PersistentEffect`（`Dimension = null` 的提示标记类效果）、`WitchCurseTrigger`、
  `DayActions` 的白天契约闸、说书人效果链、玩家视图白名单。

### R-0020 · 处罚处决与「每个白天最多一次处决」

- **状态**：Decided
- **问题**：洗脑师与畸形秀演员的「处罚处决」（说书人主动处决）在线上怎么记账？占不占当天的处决上限？白天处罚后白天怎么收口？夜晚处罚算什么？
- **依据**（均为 2026-10-01 抓取）：
  - 百科《洗脑师》· 角色简介 7 —「像畸形秀演员一样，执行处决惩罚计入每天的处决限制」；
    · 运作方式 —「在下一个白天或夜晚，如果被选择的玩家没有尽最大努力去说服其他玩家他是被选择的角色，
    你就可以处决他。向所有玩家宣布他的死亡。如果你在白天的常规处决前处决了他，则直接进入夜晚阶段。
    （每个白天最多一次处决。）」
  - 百科《畸形秀演员》· 角色简介 5 —「如果你认为他正在以任何方式证明自己是一名外来者，你就可以处决他，
    即使在提名阶段之外，甚至是在晚上都可以处决他。如果你这样做，正常情况下这意味今天白天不会再有其他人
    被处决，因为每个白天只有一次处决」；· 角色简介 6 —「如果畸形秀演员晚上暗示他是畸形秀演员，那么你在
    当晚可以处决他，**即使今天白天已经有人被处决**。宣布他的死亡，并正常进行夜晚。明天仍然可能发生一场
    处决」；· 运作方式 —「如果这次处决发生在白天的常规处决之前，则直接进入到夜晚阶段。
    （每个白天最多能进行一次处决。）」
- **处理（默认行为，代码注释必须引用本条）**：
  1. **白天处罚处决占用当天上限**并立即收口白天（直接进入夜晚）：顺序产出「被处决」事实 → 目标存活时
     记死亡 → 白天的 `DayClosedEvent`，白天账记该处决；此后当天不能再处决；
  2. **夜晚处罚处决不占任何白天的上限**：不写白天账、不推进阶段，当晚之后的下一个白天照常可以处决
     （《畸形秀演员》角色简介 6 的明文例外；洗脑师处罚按"每个白天最多一次处决"同理）；
  3. **已死亡的目标仍可被处罚处决**：只记「被处决」这一事实，不重复记死亡（处决 ≠ 死亡，百科《处决》）；
  4. **存在未计票的提名时先计票**（平台收口口径）：处罚处决被显式拒绝，沿用白天票 `ForceAdvance` 的
     同一处理——平台不替说书人拍板计票结论，也不让白天账留下停在投票中的提名；计票后说书人仍可立即处罚，
     这一条不改变规则上的"任何时刻"；
  5. 处罚处决的死亡原因按来源区分（`cerenovus.madness` / `mutant.madness`），带归因进事件流；
  6. **白天已关闭、夜晚尚未开始的间隙窗口**按夜晚形态处理（`DayNumber = null`，不写白天账）：
     那一刻白天的常规处决已经不存在，不存在可占用的当日上限；命令面在该窗口仍然可达，
     属登记在案的平台口径，不是静默默认。
- **影响面**：`ExecutedEvent`（新增 `Kind` 与可空 `DayNumber`）、`DayRecord`、`AdjudicatedExecutionMachine`、
  `PunishExecutionCommand`、说书人处罚控件、集成与装置用例。

### R-0022 · 玩家的公开生死面包含什么、什么时点公开

- **状态**：Decided
- **问题**：死亡（与复活）在玩家端公开什么、什么时候公开、死因要不要公开？此前"死亡是否可见"
  取决于死因——处决有公开事实 `Executed`，夜间击杀与咒杀对玩家完全不可见，玩家只能靠外部语音得知。
- **依据**（均为 2026-10-01 抓取）：
  - 百科《术语汇总》· 城镇广场 / 生命标记：「城镇广场上会有玩家的生命标记和投票标记」；
    「生命标记：……会展示有哪些玩家存活或已死亡。标记较亮的一面表示该玩家存活，较暗的一面表示该玩家已死亡。」
    ——生死状态本来就是桌面上的公开信息，不是说书人专属资料；
  - 百科《规则概要》· 二·黎明：「当夜晚阶段到达黎明时，等待五到十秒，然后告诉所有玩家睁眼，
    并宣布这个夜晚死亡和复活的玩家（**相对于黄昏而言生死状态发生了变化的玩家才会宣布**），
    **但不告诉玩家他们的死亡和复活原因为何**。」；《夜晚行动顺序一览》· 黎明同义；
  - 百科《小恶魔》· 运作方式：「黎明时，宣布有哪名玩家在夜晚死去。（不要说明死亡原因。）」；
    《僧侣》· 运作方式：「在黎明时，宣布当晚无人死亡。（不要解释原因。）」——黎明公告是固定动作，
    没有变化就宣布"无人死亡"；
  - 百科《女巫》· 运作方式：「下个白天，如果被标记为'被诅咒'的玩家发起了提名，**立即宣布他死亡**。
    （提名正常进行）」——白天发生的变化即时公开；
  - 百科《规则概要》· 三-3：处决阶段说书人宣布处决与死亡（处决 ≠ 死亡，见《处决》）；
  - 百科《洗脑师》· 运作方式：「**向所有玩家宣布他的死亡**」——处罚处决的死亡属公开面，
    但处罚的**理由**（疯狂要求）不在其列（R-0020 / R-0021）；
  - 百科《死亡触发能力》：存在"**已死亡但未得知死讯**"的状态——公告时点之前，死亡对本人也不可见。
- **处理（默认行为，代码注释必须引用本条）**：
  1. **公开面 = 生死状态 + 生死变化公告**：全体席位的"对外可见生死"（生命标记的等价物）+
     相对黄昏发生变化的席位公告。**不含死因、不含能力归因、不含说书人的生死账 / 效果账**；
     玩家自己的生死也在其中——死亡后他自己的界面必须显式可见（据此判断还能不能提名 / 投票，
     见《重要细节》三-1 与《规则概要》三-3）。
  2. **时点**：夜晚期间的变化**累积到黎明**（下一个白天开始）一次性公开，按"相对黄昏的**净变化**"
     计算——夜里死而复生者不公告；白天发生的变化**立即公开**（女巫"立即宣布"的等价物，
     处决 / 处罚处决的死亡随其提交公开）。**黄昏边界**：以白天关闭（`DayClosedEvent`）为界——
     白天关闭之后、夜晚计划开始之前发生的变化按夜晚形态累积到下一个黎明（与第 6 条的间隙窗口同族，
     在此登记在案，不做"间隙内即时公告"的静默默认）。
  3. **死因不公开**：公告只有"谁死了 / 谁复活了"；夜间击杀、咒杀、处罚处决的来源、能力与疯狂要求

  4. **未公告不算数**：生死变化在公告时点之前不得下发给任何玩家（含本人）——第 7 条依据里的
     "已死亡但未得知死讯"是真实存在的状态。
  5. **复活与死亡同列公告**；公告只描述"对外公开了什么"，不改变真实生死账（D-0015）。
  6. **平台口径（登记在案）**：夜晚发生的处罚处决（畸形秀演员 / 洗脑师）的"宣布他的死亡"

     （通则见第 2 条）；白天处罚处决则随其提交即时公开（R-0020 的白天形态立即收口白天）。

### R-0024 · 胜负判定的时机与优先级

- **状态**：Decided
- **问题**：胜负在哪个边界判定、按什么优先级、判出来之后还能不能继续操作？
- **依据**：
  1. 百科《处决》· 2026-10-01 抓取 · 一些相关效果的触发时机：第 3 步「检查是否达成游戏结束的条件」
     先于第 4 步「结算其他与处决相关或者由死亡触发的能力……呆瓜等」；并明确「如果游戏在第三步骤中结束，
     则相应的其他在本步骤中触发的效果都不会进行结算」；
  2. 百科《特殊胜利失败条件》· 2026-10-01 抓取：一方满足特殊胜利条件优先于另一方满足常规条件；
     双方同时满足特殊条件 → 善良获胜；同时满足常规条件 → 善良获胜；
  3. R-0008：一次结算事务内连续产生的死亡不中途判定，事务提交后统一判定。
- **处理（默认行为，代码注释必须引用本条）**：
  1. **判定点**：一次原子提交的**业务事件折完后先判一次**（对应《处决》第 3 步）；未结束才跑
     事件触发 / 常驻对账，随后**再判一次**（触发产出的死亡同样可能满足胜负条件，事务内不中途判）。
  2. **优先级**：特殊条件 > 常规条件；同一层内双方同时满足 → **善良获胜**。
  3. **首版层级**：「照看小怪宝的最后一名恶魔死亡」层不在首版剧本，登记不实现。
  4. **没有任何恶魔角色时不判**：常规善良条件读作"存在至少一名恶魔角色，且它们全部死亡"。
     纯空集不算"所有恶魔均已死亡"——配置错误 / 非剧本夹具不该被静默判成一局结束
     （装置与集成夹具的小席位局面就靠这条区分"规则结束"与"配置异常"）。
     **2026-10-05 细化（见 R-0029）**：本条针对的是**本局从未出现过恶魔角色**的配置异常；
     运行期由角色变更（麻脸巫婆等）造成的「恶魔清零」按 R-0029 判善良获胜。
  4. **结果**：产出唯一一条 `GameEndedEvent`（胜方 + 条件分类 + 说明）；此后一切命令被拒
     （`phase.game_ended`，含说书人命令）；重放只折事件，不重判。
- **影响面**：`OutcomeEvaluator` / `GameEndedEvent` / `StepMachineState.Outcome` /
  `GameSession` 提交编排 / 命令闸 / 投影与通知。

  - 百科《夜晚行动顺序一览》· 麻脸巫婆条：「请注意：即使麻脸巫婆的顺序改变，
    她的能力造成死亡的时机仍然需要等到首个能够造成死亡的恶魔角色行动之前」。
- **处理（默认行为，代码注释必须引用本条）**：
  1. **窗口**：麻脸巫婆的结算**创造了恶魔**（结算后角色类型为恶魔，含「恶魔 → 另一种恶魔」）时，
     当晚进入死亡裁量窗口；窗口从该槽位结算后开始，到**计划里最后一个恶魔角色槽位结束**为止；
     期间麻脸巫婆自己离场 / 死亡**不关闭**窗口；
  2. **待定死亡**：窗口内的恶魔击杀**不直接产生死亡**，而是记为待定（目标 + 来源席位 + 能力 + 发生槽位）；
     说书人逐条裁定「确认」或「阻止」——确认产死亡事实（来源为恶魔席位），阻止只记阻止事实；
  3. **平台口径（登记）**：窗口关闭时仍未裁定的待定死亡，**按恶魔攻击的自然结果生效**（死亡），
     并在事件里写明「窗口关闭时未裁定，按默认结果生效」——这是显式记录，不是静默默认；
     说书人若要免死，必须在窗口内裁定「阻止」；
  4. **追加死亡**：窗口内说书人可随时追加死亡（任意玩家，含尚未行动的恶魔）；该类死亡**归因为麻脸巫婆**
     （`CausedBy` = 麻脸巫婆席位），不触发「被恶魔杀死」类能力；窗口关闭后该命令被拒
     （`phase.pit_hag_window_closed`）；
  5. **只加不减**：本机制不提供「复活」或「阻止非恶魔造成的死亡」的路径；
  6. **「新恶魔当晚行动」与「杀死未唤醒的恶魔」** 由槽位进入时按当前账求值自然实现
     （行动者已死亡 → 空槽位；角色刚被创造 → 行动槽位），不在裁量窗口里另开通道。
- **影响面**：`StepMachineState.PitHagNight` / 待定死亡事件族 / `AbilityResolutionContext`（窗口标志）/
  恶魔击杀契约的死亡产出口径 / `PitHagCasualty` 与 `ResolveDeferredDeath` 两条命令 / 说书人投影与面板。

### R-0033 · 理发师「死亡触发 → 当夜交互」的平台口径

- **状态**：Decided（平台口径，登记在案）
- **问题**：理发师的「如果你死亡，在当晚恶魔可以选择两名玩家交换角色」把两件事分开：
  死亡时立即触发、涉及交互的效果要等到夜晚；平台怎么排期、事实怎么收口、多恶魔与「摇头」怎么表达？
- **依据**（均为 2026-10-01 抓取）：
  - 百科《理发师》· 角色能力——「如果你死亡，在当晚恶魔可以选择两名玩家（不能选择其他恶魔）交换角色」；
    · 提示标记「今晚理发」——放置条件「理发师死亡且此时未醉酒中毒」、移除时机「能力触发、
    恶魔执行交换（或放弃）后」；· 运作方式——「在理发师死亡的夜晚，唤醒一名恶魔玩家」、
    恶魔摇头 = 不交换、可选自己与已死亡玩家、不能选择另一名恶魔；· 角色简介——
    「必须作为理发师死亡才触发」（死亡之后才变成理发师不触发）；
  - 百科《死亡触发能力》· 能力简介——这类能力在死亡时立即触发，涉及交互的效果
    「需要等到夜晚的时候再进行交互」；《夜晚行动顺序一览》· 其他夜晚——理发师格在恶魔段之后。
- **处理（默认行为，代码注释必须引用本条）**：
  1. **死亡触发 → 当夜交互**：死亡事件落账时**立即**记「今晚理发」事实（`BarberNight`）；
     与恶魔的交互发生在当夜顺序表的**理发师格**（触发格，`StepSlotKind.Trigger`）——
     那一格进入时由触发器向恶魔开操作请求。白天本身不发生交互。
  2. **事实生命周期**：白天 → 夜晚**跨阶段保留**（白天处决 / 死亡 → 当夜交互）；
     夜晚计划走完仍未消费时由推进路径**显式清空**并记「过时不候」，不顺延到下一夜；
     夜晚未收口就进入新阶段属于事件流损坏，恢复必须**显式失败**。
  3. **出生即过期（登记）**：死亡发生在理发师格之后、或当夜顺序表根本没有理发师格（首夜）时，
     不记事实、不开请求，只留一条可归因的跳过记录；死亡就发生在理发师格时，同一批补开交互。
     当前剧本内的死亡都发生在理发师格之前，这一条覆盖的是登记在案的边界，不是静默默认。
  4. **选择形态**：一次**原子选择** = 合法玩家对（编码 `pair:小+大`，升序规范化）+
     「不交换」（`decline`，恶魔摇头的等价物）；候选对排除「另一名恶魔」（执行交换的恶魔本人
     可作为两人之一）；可选自己与已死亡玩家；两名以上存活恶魔时由**说书人先裁定**用哪名恶魔，
     再向他开请求（该裁定点归属触发管线，不由行动槽位结算推进）。
  5. **结算**：交换只写**角色维度**（阵营不变，六维度独立）；`PreviousCharacter` 由产出方显式给全
     （R-0029 的胜负判据要用）；尚未进入的槽位按 R-0032 重绑给新持有者，已经进入过的不重绑；
     请求为**槽位来源**（挂在理发师格上）：挂着不推进、答完继续走、作废 / 强推时显式关闭事实。
  6. **死亡时醉酒 / 中毒**：不放置事实、恶魔当夜不能交换（提示标记的放置条件）；
     这两维未观测同样不放（不猜，D-0015），并留下跳过记录。
- **影响面**：`StepMachineState.BarberNight` / `BarberNightOpenedEvent` / `BarberNightClosedEvent` /
  `BarberNightSkippedEvent` / `StepSlotKind.Trigger` / `NightOrderEntryKind.CharacterTrigger` /
  `BarberNightTrigger` + `BarberSwapInteraction` / `StepMachine.HandleDecisionResolved`（裁定点归属）/
  `DayActions`；回归见 `BarberNightTests` / `BarberNightTriggerTests` / `BarberHostTests`。

### R-0034 · 方古侵染与麻脸巫婆之夜「死亡裁量窗口」的交互口径

- **状态**：Decided（平台口径，登记在案）
- **问题**：方古「首次成功杀死外来者时，改为方古死亡、外来者变成邪恶的方古」——这次攻击的**自然结果是转化，不是死亡**。

- **依据**（均为 2026-10-01 抓取）：
  - 百科《方古》· 角色简介 2——「方古首次攻击并成功杀死外来者时，改为方古死亡，外来者变成邪恶的方古」；
    · 运作方式 11–14——被选择的外来者变成新方古、原方古旁放「死亡」标记、「限一次」标记放在魔典中心；
    · 提示标记「限一次」——放置条件「在方古成功触发能力转化外来者时」、移除时机「持续至整局游戏结束」；
    · 范例——「方古攻击死去的呆瓜。因为呆瓜已经死了，他不会再次死亡，所以方古不会死」；
  - 百科《麻脸巫婆》· 规则细节 1——窗口期内「说书人能够自由决定是否让某名玩家死亡，或让被恶魔攻击的某名玩家存活」
    （R-0030 第 2 条的平台口径：待定死亡由说书人确认 / 阻止，未裁定的按自然结果生效）。
- **处理（默认行为，代码注释必须引用本条）**：
  1. **待定死亡携带转化载荷**：窗口期内方古对「外来者 + `限一次`未用」的攻击记为一条待定死亡，
     载荷写明「确认后的结果是转化」而不是死亡；载荷由方古契约产出，内核只按它落事实（不硬编码角色 slug）。
  2. **确认 = 按能力转化**：外来者变成新的**邪恶**方古、原方古死亡、「限一次」标记落下；**被攻击者本身不死亡**。
  3. **阻止 = 击杀与转化都不发生**：外来者存活且仍是原角色，原方古存活，「限一次」标记不消耗。
  4. **原方古之死不可单独阻止**：它是转化结果的一半，平台不提供「只阻止原方古死亡」的路径。
  5. **确认时目标已经死亡 → 整体不发生**：没有「成功杀死」这回事，原方古不死、标记不消耗
     （与范例「呆瓜已经死了……所以方古不会死」同口径）；裁定本身仍留在事件流里。
  6. **窗口关闭仍未裁定** → 按同一条载荷走默认结果：R-0030 第 3 条的「自然结果」对这条攻击就是**转化**，不是死亡。
  7. **「限一次」是整局事实**（`StepMachineState.FangGuInfection`）：跨阶段保留、重放只折事件；
     即使原方古死亡 / 换角、或之后由别的角色制造出新的方古，也不再侵染（运作方式 3 / 14）。
  8. **同名标记与角色唯一**：转化会让「已死亡的原方古」与「存活的新方古」同时持有 `fang-gu` 标记；
     角色唯一的规范对象是**存活持有者**——建表器据此把方古格绑给存活的那一位（R-0029 同族口径：
     已死亡玩家的角色标记仍留在魔典上）。
- **影响面**：`FangGuNightAction` / `DeferredTransformation` / `DeferredDeath`（含 `Recorded` 事件）/
  `PitHagNightMachine.AppendOutcome` / `NightPlanBuilder` 的持有者判定 / `StepMachineState.FangGuInfection` /
  `DeferredDeathDto.Transformation`（说书人面板文案）；回归见 `FangGuNightActionTests` /
  `PitHagNightMachineTests` / `NightPlanBuilderTests` / `FangGuInfectionTests` / `FangGuHostTests`。

### R-0038 · 贤者「被恶魔杀死」的判据与当晚展示的平台形态

- **状态**：Decided（第 3–5 条为平台口径，登记在案）
- **问题**：贤者有两处容易做错：① 「被恶魔杀死」怎么从死亡事件里读出来——处决、女巫诅咒、

- **依据**（均为 2026-10-01 抓取）：
  - 百科《贤者》· 角色能力——「如果恶魔杀死了你，在**当晚**你会被唤醒并得知两名玩家，
    其中一名是杀死你的那个恶魔」；· 角色简介 2——「贤者只有在被恶魔杀死时才会获取信息，
    死于处决时不会」；· 运作方式 1–3——唤醒贤者、指向两名玩家；两名可以是存活或已死亡玩家；
    · 范例 2——醉酒的贤者得到的是「一名死亡玩家和一名存活善良玩家」的错误信息；

  - 百科《夜晚行动顺序一览》· 其他夜晚——贤者条目；同页注释「死亡触发能力的夜晚顺序并不重要，
    仅作为能力遗漏触发时的提示」。
- **处理（默认行为，代码注释必须引用本条）**：
  1. **「被恶魔杀死」判据**：死亡事件的 `CausedBy` 席位在**死亡时刻**的角色是恶魔
     （按死亡批内事件重建死亡时刻的角色，与理发师 `DiedAsBarber` 同族）；`CausedBy` 为 null
     （处决）或非恶魔（女巫诅咒 / 处罚处决 / 麻脸巫婆追加死亡）一律不触发。

  4. **能力未生效（平台口径）**：死亡时醉酒 / 中毒（或这两维未观测）→ 照常开裁定点；
     信息照发、`MayBeFalse = true` 并带注记；内容由说书人裁量（范例 2 的错误信息形态）。
  5. **涡流在场**：信息标 `MayBeFalse` + 「必须为假」注记（R-0028）；裁定内容仍由说书人给出。

### R-0041 · 初始设置分布表（人数 → 各类型数量）的来源与平台口径

### R-0042 · 「设置调整」参与初始配板的净分布口径：先加总、再钳制、镇民补偿

- **状态**：Decided（平台口径，登记在案）
- **问题**：把角色标记上的 `[...]` 设置调整（R-0035）真正接进配板时，三件事要定口径：
  ① 多个修正同时在场怎么合成；② 修正超出可用角色（外来者不够、或把某类型压到无）怎么办；
  ③ 修正与引擎的边界。R-0035 当时只承载「界面提示」，本票把它升级为「参与净分布计算」。
- **依据**（均为 2026-10-04 抓取）：
  - 百科《设置调整》· 能力简介：「部分设置调整能力会对特定角色类型做出数量调整，在这种时候如无特殊说明，
    默认会对镇民的数量做出相应的调整。（如+1外来者则意味着同时需要-1镇民……）」；
  - 同页 · 优先级 4「基础配置变动」：「这类配置变动会**首先加总所有变化**，随后再判断是否满足当前剧本中的
    外来者数量区间，最后才进行相应的调整。」例：11 人（7/1/2/1）中 −2 而只有 1 个外来者
    →「实际效果让外来者总共-1，且镇民+1」；12 人（7/2/2/1）中 +3 而剧本只有 4 个外来者 → 最终 4、
    「实际效果让外来者总共+2，且镇民-2」；11 人中 +1 与 −1 同时在场 →「让外来者数量不发生变化」；
  - 同页 · 相关角色（基础配置变动）：《梦殒春宵》只有两名——方古「+1外来者，-1镇民」、亡骨魔「-1外来者，+1镇民」；
  - 同页 · 能力简介：「在游戏开始后，设置调整能力不再产生任何效果」；R-0035 第 3 条延续；
  - D-0008 / D-0011（随机只作显式输入）、D-0017（分配即事件，提交走既有命令面）。
- **处理（默认行为，代码注释必须引用本条）**：
  1. **合成顺序**：同类修正先**加总**（不逐条先后钳制），再加到基线表上得到「期望分布」；
  2. **钳制**：期望值按 `[0, 可用上限]` 钳制；可用上限取「剧本该类型角色数」与「总人数约束
     （镇民 + 外来者 + 爪牙 + 恶魔 = 玩家人数）」的较小者。**「修正超池」按官方口径钳制，不判失败**；
     钳制必须**显式披露**：配板建议里逐条给出「期望 → 实际」的说明（不静默改写、不悄悄降级）；
  3. **补偿与残余失败面**：镇民 = 玩家人数 − 恶魔 − 爪牙 − 外来者；若最终任一类数量为负、
     或基础分布本身超出剧本池（脚本层面根本配不出）→ 显式失败（`setup.distribution_conflict` /
     `setup.pool_exhausted`）；人数不在表内（<5 / >15）→ `setup.player_count_unsupported`；
  4. **边界**：修正只影响初始设置，不进引擎判定、不在夜里补任何效果（R-0035 第 3 条延续）。
     本版只实现《梦殒春宵》的固定值修正（方古 +1 / 亡骨魔 −1）；**范围型修正**（「+0~1 外来者」一类）
     与**增减恶魔 / 特殊设置方式 / 认知覆盖 / 增加特定角色**（《设置调整》优先级 1–3、5）**不做**，
     登记为非目标；数据模型按「目标类型 + 整数增量」建，将来可扩展；
  5. **随机与落账**：配板的随机只作显式输入（种子），求解是纯函数、同种子同结果；
     建议是**瞬态**的——不落账、不进事件流；说书人可重摇 / 手改，提交仍走既有分配命令面（D-0017），
     事件流里只有显式分配，重放不重摇（D-0008 / D-0011）。
- **影响面**：`SectsAndVioletsRoster`（设置修正数据，方古 +1 / 亡骨魔 −1）、
  `SectsAndVioletsDistribution`、配板求解（Rules）、建议查询面（Application / Server）、
  `AssignmentControl.vue`（净分布与钳制说明）；回归见修正合成 / 钳制 / 失败面用例与装置段。

### R-0043 · 复盘对局内玩家开放后能揭示到什么程度

- **状态**：Decided（平台口径，登记在案）
- **问题**：自动化复盘要回放事件流里的全部事实（夜间行动、说书人裁量、信息真假、死亡归因）。这些在游戏进行中是隐藏信息：结束之后对局内玩家揭示到什么程度？说书人的实时面与玩家的终局面怎么分开？
- **依据**：
  - 票据 `docs/backlog/done/replay-auto-review.md`（2026-10-04 登记）——「复盘在游戏进行期间不得给玩家提前泄露任何隐藏信息」
    「只有本局结束（`GameEndedEvent`）之后才允许对局内玩家开放」；「结束后的揭示范围（是否全量揭示夜间与裁量事实）在开工时定稿并登记裁定——
    默认按『终局揭示』处理，但**不得**借复盘把说书人当下的裁量提前暴露」；
  - D-0012（信息隔离在服务端强制）、D-0010（事件是唯一事实来源）、R-0024（结束后局面冻结、一切命令被拒）。
- **处理（默认行为，代码注释必须引用本条）**：
  1. **玩家面闸门**：`GameEndedEvent` 之前，对局内玩家**零复盘字段、零复盘数据**——复盘不塞进任何进行中的投影 / 推送包；
     玩家发起的复盘查询在服务端被显式拒绝并记审计（不靠前端隐藏）。
  2. **终局揭示**：结束批次之后，复盘对**对局内玩家**开放，按「终局揭示」给出全部对局事实：
     夜间行动与目标、死亡与归因（含「被恶魔击杀」判据）、五维状态变化及原因、能力结算与生效判定、
     信息结果及其「可能为假」标记、裁定点与说书人的选择、白天提名 / 投票 / 处决结论。
     **说书人注记（D-0019）不在此列**——它在任何形态的复盘里都不下发（自由文本不是对局事实）。
  3. **说书人面**：说书人已有上帝视角，复盘对其是**实时面**（进行中即可查看；同一份投影，无新事实、无新账本）。
  4. **不新增事实源**：复盘是事件流的呈现投影，任意时刻可由「快照 + 序号之后的事件」重建；刷新 / 重连按事件序号恢复数据与位置。
  5. **改口径走新裁定**：将来若要「赛后仍不揭示某些内容」，新增裁定条目并补回归；禁止就地改默认或按接收者临时过滤。
- **影响面**：`ReplayProjection` / `GameSession.GetReplay` 的可见性闸、终局后可见的玩家契约类别、前端 `features/replay`、
  零信任装置的反方向断言、`docs/decisions/active.md` D-0020。
