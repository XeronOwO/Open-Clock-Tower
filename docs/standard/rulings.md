# 裁定登记表（Ruling Register）

> 本表是本项目的**一等交付物**，不是附录。
> 规则里凡是「查不到、拿不准、百科自相矛盾、需要项目自定」的，都必须在这里有一条记录。
> **禁止**把不确定的行为直接写进代码然后当它不存在。

## 为什么必须有这张表

《血染钟楼》的规则由三部分构成：**印刷规则书** + **钟楼百科的角色详解** + **说书人的现场裁定**。
前两者都无法覆盖全部组合（百科自己就写了"三角色相克短期不会整理"），
于是大量行为只能落到"项目怎么算"。这些"项目算"如果散落在代码里，
后人读到就只有默认行为、看不到它其实是**一个未经确证的选择**——这正是本项目要根除的事故源。

## 状态定义

| 状态 | 含义 | 代码侧义务 |
|---|---|---|
| `Open` | 有疑问，尚无可靠依据 | 默认行为处必须写注释引用裁定号；禁止静默生效 |
| `Decided` | 已有依据（百科原文 / 官方设计师回复 / 用户明确决定） | 依据必须可复核（页名 + 抓取日期） |
| `Contested` | 多处依据互相冲突 | 记录冲突双方，暂取其一并说明；对局前须告知玩家实际口径 |
| `Deferred` | 本项目暂不实现 | 必须同时在 UI/文档显式声明"本版本不支持"，禁止静默缺失 |
| `OutOfScope` | 明确不做 | 记录原因与解除条件 |

### R-0001 · 剧本正名：梦陨春宵 → 梦殒春宵

- **状态**：Decided
- **问题**：需求方口语／输入法习惯写作「梦陨春宵」，百科官方译名为「梦殒春宵」。
- **依据**：钟楼百科页《梦殒春宵》（Sects & Violets）；需求方会话确认二者指同一剧本。
- **处理**：全项目统一使用「梦殒春宵」，英文 slug 为 `sects-and-violets`。
  「梦陨春宵」作为**别名**录入 `terminology.md`，用于检索与纠错提示，不用于任何标识符或界面文案。
- **影响面**：术语表、界面文案、角色数据目录名、文档。

### R-0002 · 三角色相克如何处理

- **状态**：Open（部分已定）
- **问题**：三个角色互相构成相克时如何裁定，例如「麻脸巫婆把一名邪恶玩家变成哲学家，该哲学家又选择获得异端分子的能力」。
- **依据**：百科《相克规则》原文——"三角色问题会比双角色问题更加复杂，需要考虑的东西更多"，因此
  "在短期内（话先不说死）不会整理'三角色相克'规则"；百科只给了一条类比范例。
- **处理**：
  1. MVP 的相克解析器**只判定双角色相克**。
  2. 遇到三角色及以上组合时，解析器必须返回「未登记」这一**显式结果**，交给说书人现场裁定。
  3. 引擎**禁止自行类推**；裁定完成后追加一条本表条目，并把它变成可回归的测试用例。
- **影响面**：`Rules` 层相克解析器的返回类型必须能表达"未知"，不能只有"冲突/不冲突"两态。

### R-0003 · 疯狂是否可由引擎自动判定

- **状态**：Decided
- **问题**：「疯狂」要不要建成内核里的一个状态位，由引擎判断玩家是否"疯狂地证明了某件事"？
- **依据**：百科《重要细节》三-4 明确——疯狂"更像是一个现实中的状态。你无法在魔典中查看一名角色是否疯狂"，
  且"你作为说书人，有对玩家的表现是否符合'疯狂'状态的最终裁决权"。
- **处理**：
  1. 疯狂**不建为引擎状态**，玩家状态仍只有 角色/阵营/生死/醉酒/中毒 五项可在魔典中观测，
     另加一项**仅由裁定写入**的 `MadnessRequirement`（谁、在何时、被要求疯狂证明什么）。
  2. 引擎负责：产生要求、计时提醒、承接说书人裁定（成立/不成立）、按裁定触发后果（如处决）。
  3. 引擎**不负责**判断玩家发言是否满足疯狂。
- **影响面**：内核领域模型；洗脑师、畸形秀演员、哥布林等角色的实现；说书人端交互。

### R-0004 · 「能力未正常生效」的计数口径（数学家）

- **状态**：Open
- **问题**：数学家得知"有多少能力未正常生效"。到底哪些情形计入、哪些不计入？
- **依据**：百科已经给出**互相区分**的三类结论，散落在不同页：
  - 《相克规则》开头：「所有因相克规则而导致自己能力未正常生效的，**不会**计入到数学家的能力检测中」。
  - 《占卜师》规则细节：因"干扰项"而得知"是"**不计入**（这是能力自身设定的正常结果）；
    但醉酒中毒时选中干扰项却得知"否"**计入**（能力确实未正常生效）。
  - 《相克规则》：数学家与酒鬼/提线木偶的组合各有单独说明。
- **处理**：为每条"可能导致能力未正常生效"的路径标注一个 `MalfunctionKind`
  （中毒 / 醉酒 / 相克 / 涡流 / 咖啡师 / 能力自身设定 / 说书人裁定 / 未定）。
  口径未逐条核对完之前，相关路径一律标 `Open` 并计入待核对清单。
  - **2026-10-01 核对补充**：《数学家》页「角色简介 / 运作方式」明确——数学家不会得知异常发生在哪名玩家身上；
    不会检测自身是否未正常生效；不会检测中毒和醉酒状态本身，而是检测"因为这些状态而没有按预期发挥作用的能力"。
    7 条相关相克条目已录入 `character-rules.md`；口径仍未闭合（逐条 `MalfunctionKind` 待对表）。
  - **2026-10-02 补充（结算引擎落地）**：同一名玩家**同时中毒且醉酒**时，能力未生效是确定的
    （百科《重要细节》三-3：醉酒与中毒互不抵消），但这条失效该归入哪一类、计几次，尚未核对到依据；
    实现一律记 `MalfunctionKind.Open` 并留在待核对清单（`MalfunctionLedger.Unclassified`）里，
    不许硬塞进"中毒"或"醉酒"。
- **影响面**：内核的失效账本；数学家角色实现；所有信息类角色的实现。

### R-0005 · 相克规则与「不能最大」的优先序

- **状态**：Open（暂定序已用于实现，等待确证）
- **问题**：相克规则是"规则"而不是角色能力（百科明确说明）。当相克规则与角色能力冲突、
  或相克规则与"不能最大"原则冲突时，谁优先？
- **依据**：百科《相克规则》："相克规则是规则而非灯神的能力"；
  百科《钟楼谜团隐性规则汇总》第 2 条"不能最大"：两个能力冲突时以"不能"的一方生效。
- **处理**：实现采用**暂定优先序**：`相克规则 > 不能最大 > 角色能力 > 核心规则`。
  **此序未获百科确证**，属于项目自定口径；一旦出现反例立即改此处并同步改代码。
- **影响面**：内核冲突解析器（决定性模块）；说书人端的裁定提示。

### R-0008 · 连续死亡过程中是否插入胜败判定

- **状态**：Decided
- **问题**：一次结算里造成多名玩家先后死亡时，是否在中间就判断胜负？
- **依据**：百科《钟楼谜团隐性规则汇总》第 5 条明确——"痢蛭的宿主与痢蛭的先后死亡的过程中

### R-0012 · 来源醉酒 / 中毒时，持续型效果是「终止」还是「挂起」

- **状态**：Contested（暂取「挂起」，等待更权威条文）
- **问题**：百科同一段里先说这种效果"会终止"，紧接着又要求"恢复后继续生效"。平台按哪种建模？
- **依据**（2026-10-02 核对 `references/wiki/重要细节.wiki` 快照）：
  - 冲突一方 · 二-3（第 23 行）："角色能力会在死亡，中毒或醉酒的那一刻立即失去，
    **同时能力产生的所有持续型效果也会终止**。"
  - 冲突另一方 · 同段下半句 + 三-3（第 125–130 行）："如果角色从中毒或醉酒中恢复健康和清醒，
    角色能力和**原本已经生效的持续型效果也会继续生效**"；范例：茶艺师中毒 → 不再保护邻近玩家，
    恢复健康 → 再次保护；女巫醉酒 → 诅咒失效，恢复清醒 → 诅咒恢复。
  - 旁证 · 二-4（第 33 行）："这些能力仍然会在玩家醉酒或中毒时**暂时**失去"。
- **处理**：取**挂起**（suspension）：
  1. 来源醉酒 / 中毒 → 效果**不终止**，只是当前不生效（`PersistentEffect.IsOperative` 为 false）；
     来源恢复清醒健康后**继续生效**，且**不是重新施加**（同一个 `EffectId`）。
  2. 只有**来源死亡**（二-3 投毒者范例）或**来源换了角色、失去原角色能力**（二-7）才是不可逆的**终止**。
  3. 二-3 里"终止"一词按"立即失效"理解；与同段后半句及三-3 的范例冲突时，以后者为准。
  4. **终止不可逆，但"重新获得同一能力"是另一回事**：来源复活、或换走之后又换回原角色时，
     角色能力重新生效 → 产生**新的一条效果**（新的 `EffectId`，如 `…:2#2`），
     而不是让已终止的旧效果复活。结算对账按这条规则处理（`SettlementReconciler` 的世代规则）。
- **代码侧义务**：`PersistentEffect` 与 `GameStateMachine` 的相关注释必须引用本条；
  `EffectAttributionTests` / `EffectLifecycleTests` 的挂起与恢复用例是本条的回归。
- **影响面**：`PersistentEffect.IsOperative`、`GameStateMachine` 的来源失效传播、`GameState.OperativeEffectsOn`、
  后续结算引擎"按仍生效的效果重算维度"。

### R-0013 · 即时型效果是否随来源失效而回滚

- **状态**：Open
- **问题**：已经生效的即时型效果（恶魔击杀、猎手开枪…）在来源之后死亡 / 醉酒 / 中毒时要不要撤销？
- **依据**：仓库内**唯一直接**的表述是《重要细节》三-3 的注（第 126 行）：
  "生死类互动干扰能力是例外……在醉酒中毒时只会让持续型效果部分失效，但即时型效果部分
  **因为已经生效所以不会再变为无效**"——它只覆盖**醉酒 / 中毒**一种情形，没有覆盖"来源死亡之后"。
  二-3 只说明"持续型效果会终止"，未直接说明即时型效果。
  因此当前实现取"不回滚"，属于**从沉默反推**，按本表规则必须显式登记而不是当作已确证。
- **处理**：
  1. 暂取"**不回滚**"（`InstantaneousEffect.RemainsInEffect()` 恒为 true），代码注释引用本条。
  2. 拿到印刷规则书或设计师回复中覆盖"来源死亡"的条文后改为 `Decided`；
     若出现反例，改为回滚并同步改代码与测试。
- **影响面**：`InstantaneousEffect`；所有即时型能力（恶魔击杀、猎手、刺客…）的结算与回退。

### R-0015 · 开局分配是否同时记录「初始生死 = 存活」

- **状态**：Decided
- **问题**：建表需要每个在场角色的生死，而状态账坚持「未观测 ≠ 默认值」（D-0015）。
  如果开局只记录角色、不记录生死，第 2 夜起幸存者的生死会一直是未知，引擎只能猜或拒绝建表。
- **依据**：
  1. 百科《规则概要》· 2026-10-01 抓取 · 一-4「准备城镇广场」：
     "在城镇广场上与每名玩家座位对应的位置放置一个生命标记。"——开局给每名玩家放的就是生命标记；
  2. 百科《重要细节》· 2026-10-01 抓取 · 三-1：「通常来说，玩家会在白天因为处决而死亡，
     或在夜晚因为一些角色能力而死亡。」——处决与角色能力都发生在游戏开始之后，首夜之前没有死亡来源。
- **处理**：开局分配命令（`AssignCharactersCommand`）在**同一条事件**里记录角色与初始生死 = 存活。
  这是"补全初始条件"，不是运行期把两个维度耦合：运行期的状态观测仍遵守「一次只报本次观测到的维度」。
- **影响面**：`AssignCharactersCommand`、建表器对生死的要求（未观测即拒绝，不猜）、后续设置面板。

### R-0016 · 开局分配是否同时记录「初始清醒 / 初始健康」

- **状态**：Decided
- **问题**：R-0015 只让开局分配记录「角色 + 初始生死」。但结算引擎判「能力是否生效」要读来源的
  生死 / 醉酒 / 中毒三个维度（百科《重要细节》三-3）。醉酒与中毒没有初始值，引擎按"不猜"原则
  只能拒绝结算——首夜会直接卡死。
- **依据**：
  1. 百科《重要细节》· 2026-10-01 抓取 · 三-3：「在任意时间点，一名玩家一定会处于清醒或醉酒两种状态之一，
     也一定会处于中毒或健康两种状态之一」——两维在任意时刻都有确定值，不存在的只是"平台还没记录"；
  2. 百科《规则概要》· 2026-10-01 抓取 · 一-4「准备城镇广场」：开局给每名玩家放的是**生命标记**；
     开局分配发生在首个阶段之前，此时没有任何能力能造成醉酒或中毒（角色能力要等夜晚才行动）。
- **处理**：`AssignCharactersCommand` 在**同一条事件**里补全四个维度：角色 + 存活 + 清醒 + 健康。
  与 R-0015 同理，这是**补全初始条件**，不是运行期把维度耦合：运行期的状态观测仍遵守
  「一次只报本次观测到的维度」。
- **影响面**：`AssignCharactersCommand`、能力生效判定、建表对生死的同族检查。
