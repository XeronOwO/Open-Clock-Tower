# 当前架构

> 本页回答一个问题：**这套系统由哪些部分组成，依赖朝哪个方向，以及游戏逻辑为什么能算对。**
> 决策来源见 `docs/decisions/active.md`；术语以 `docs/standard/terminology.md` 为准。

## 1. 分层与依赖方向

依赖只能从上往下。`Kernel` 不认识任何框架、不认识数据库、不认识网络。

```text
        Web (Vue 3 + TS)                     ← 说书人端 / 玩家端，两个视图
              │  HTTP + SignalR
        Server (ASP.NET Core 宿主)            ← 认证、SignalR Hub、EF Core 持久化
              │
        Application (用例编排)                ← 命令/查询、裁定点编排、会话协调
              │
        Rules (梦殒春宵的角色与相克数据)       ← 角色行为实现、剧本定义、相克表
              │
        Kernel (纯规则内核 · 确定性 · 无 IO)   ← 状态、效果生命周期、结算、冲突解析、胜负
```

| 层 | 职责（单一） | 明确**不**做 |
|---|---|---|
| `Kernel` | 状态推演、效果生命周期、结算调度、冲突解析、胜负判定 | IO、时间、随机、日志副作用、持久化 |
| `Rules` | 角色能力的**行为实现**、剧本/角色/相克规则**数据** | 结算顺序的通用规则（属 Kernel） |
| `Application` | 一次"操作"的编排：校验命令 → 产生事件 → 投影视图 | 规则判定本身 |
| `Server` | 宿主、认证、Hub、仓储、快照调度 | 任何领域判断 |
| `Web` | 呈现与输入 | **不承担信息隔离**（隔离在服务端） |

**关键先例**：`Kernel` 通过**接口**声明它需要的外部能力（如"请求一次裁定"），
由上层注入。这样依赖图无环，且内核可以被纯粹地测试。

## 2. 内核领域模型

### 2.1 玩家状态：六个正交维度

依据：百科《重要细节》三——"玩家的状态有：角色、阵营、生死、醉酒、中毒、疯狂"，
且**"状态与玩家绑定，而不与角色绑定"**；"在游戏开始后，玩家的不同状态之间相互独立，互不干涉"。

```text
Seat (玩家席位)
├── Character    角色     ← 会变（角色交换、被创造、复活）
├── Alignment    阵营     ← 会变（阵营转变）；与角色无关
├── Life         生死     ← 存活 / 死亡
├── Drunk        醉酒     ← 醉酒 / 清醒
├── Poisoned     中毒     ← 中毒 / 健康
└── MadnessReq   疯狂要求  ← 只由裁定写入；引擎不判定
```

**硬约束**：这六者**不得有联合约束**。任何形如"当角色变为 X 时顺带清除醉酒"的写法都是 bug——
百科《重要细节》三明确："因其他角色能力而醉酒的玩家角色发生了变化，不会让玩家因此解除醉酒。"

### 2.2 效果生命周期：本项目最容易做错的地方

依据：百科《重要细节》二-3 与三-3。

| | 即时型 `Instantaneous` | 持续型 `Persistent` |
|---|---|---|
| 生效时机 | 立即，改变局面后即结束 | 持续存在，被持续查询 |
| 来源死亡 / 换角色（失去原能力）时 | **不回滚**（已经发生过；依据见 `rulings.md` R-0013） | **不可逆终止**（《重要细节》二-3 投毒者范例、二-7） |
| 来源醉酒 / 中毒时 | **不回滚**（R-0013） | **挂起**：不生效但不终止，恢复后继续（`rulings.md` R-0012） |
| 来源恢复时 | 不复活 | **继续生效**（同一效果，不是"重新施加"） |

**两条必须分开记录的账**：

1. **能力使用账本**（`AbilityUseLedger`）
   一次性能力在**醉酒或中毒期间被使用 = 已浪费**。百科《重要细节》三-3："如果他醉酒或中毒期间
   尝试使用自己的'每局游戏限一次'的能力，他无法在之后再次使用这项能力。使用机会会被浪费。"
   → 因此"是否使用过"与"是否生效过"是**两个独立的布尔量**。

2. **失效账本**（`MalfunctionLedger`）
   记录每一次"能力未正常生效"及其**原因**。这不是调试日志，是**游戏机制**——
   数学家要靠它给出数字。口径尚未逐条核对完，见 `docs/standard/rulings.md` R-0004。

### 2.3 触发类型

百科《角色能力类别总览》列出的是**机制族**，内核按"什么时候被求值"归类：

| 类别 | 求值时机 | 例 |
|---|---|---|
| `NightAction` | 夜晚顺序表调度 | 舞蛇人、筑梦师 |
| `OnDeath` | 某玩家死亡的那一刻 | 守鸦人 |
| `Entry` 进场能力 | 角色被创造/变更后尽快结算 | 痢蛭选宿主 |
| `PublicTrigger` 公开触发能力 | 玩家在白天公开声明 | 猎手 |
| `Retroactive` 回溯型能力 | 先记条件，后结算结果 | 杂耍艺人 |
| `ContinuousDetection` 持续检测型 | 每次被查询时重新计算 | 占卜师（干扰项动态化）、共情者 |
| `LimitedUse` 限次能力 | 正常调度 + 次数约束 | 猎手 |
| `GainAbility` 获得能力 | 改变某玩家的能力来源 | 哲学家 |
| `Interference` 干扰 | 改变其他能力的**生效与否** | 中毒、醉酒、涡流、咖啡师 |

**已落地（2026-10-02）**：`NightAction`（钟表匠 / 筑梦师 / 诺-达鲺 / 女巫）、
`ContinuousDetection` 的一角（女巫的诅咒存续条件走 `IAbilityPresence`）、
以及事件触发族 `IEventTrigger`（女巫的「被诅咒者提名即死」+ 黄昏撤下）；
`OnDeath` / `Entry` / `PublicTrigger` / `Retroactive` 仍随各自角色分批实现。

### 2.4 裁定点（DecisionPoint）

> 依据 D-0002：平台只做**记录 + 校验 + 推演**。

每个裁量点是一个**具名契约**：

```text
DecisionPoint
├── Id           稳定标识（进事件流，永不改变）
├── Context      为什么需要决定（涉及谁、哪个能力、哪一步）
├── Options[]    合法选项（引擎算出并校验过的）
├── Preview      每个选项的后果预览（由内核试算得出，不改真实状态）
└── OnNoOption   无合法选项时的行为：跳过 / 自由决定 / 阻塞报警
```

**硬约束**：

- 角色实现**禁止**自己选目标、自己摇随机数、自己决定真假信息——一律走裁定点。
- `OnNoOption` 必须显式声明。依据 `docs/standard/rulings.md` R-0009：占卜师的干扰项要求"任意善良玩家"，
  极端局面下可能无合法选项。禁止抛异常，也禁止静默跳过。
- 裁定点进事件流，因此**可回放、可撤销、可回归测试**。

### 2.5 冲突解析

结算中所有冲突走同一条判定链，顺序是**项目自定口径**（见 `rulings.md` R-0005，尚未获百科确证）：

```text
相克规则  >  不能最大  >  角色能力  >  核心规则
```

- **不能最大**（百科《隐性规则汇总》§2）：一个能力允许、另一个禁止时，**禁止方生效**。
- **角色唯一**（§4）：同一角色同时最多一个在场；能力造成角色变化时不得违反，除非明说（军团等）。
- **死亡串行**（§5）：**不存在同一时刻多名玩家同时死亡**，死亡一律按序逐个发生。
- **过时不候**（§6）：当晚某角色的时机已结算过，之后新出现的该角色当晚不再行动。
- **胜负判定时机**（`rulings.md` R-0008）：一次结算事务内连续产生的死亡**不中途判胜负**，事务提交后统一判定。

### 2.6 结算引擎

```text
夜晚阶段
  ├── 建表：按剧本的夜晚顺序表展开今晚的步骤序列
  ├── 逐步推进：每一步 → 求值触发条件 → 需要裁定则暂停等说书人
  ├── 允许插入：OnDeath / Entry 触发的步骤插到当前位置
  └── 束：结算事务提交 → 统一判定胜负 → 产出事件
白天阶段
  ├── 提名（同日每人一次 / 被提名一次）
  ├── 投票（死亡玩家仅剩一次机会，且需有投票标记）
  ├── 判定：票数最多 且 ≥ 存活人数一半；与他人并列最多则均不处决
  └── 处决（处决 ≠ 死亡）
```

### 2.7 步骤机与操作请求（D-0011）

"自动步骤系统"不是一个 UI 特性，它是内核里的一台状态机。

```text
StepMachine（步骤机）
├── 当前阶段：首夜 / 其他夜晚 / 白天 / 结算中
├── 当前步骤：夜晚顺序表上的第 k 步
├── 挂起点：本步是否在等某个请求被响应
└── 产出：操作请求 / 裁定点 / 事件
```

**两个受众不同的原语，同源不同投影**：

| | `DecisionPoint` 裁定点 | `OperationRequest` 操作请求 |
|---|---|---|
| 问谁 | **说书人** | **玩家** |
| 例子 | "占卜师的干扰项选谁？" | "1 号，请选择两名玩家查验" |
| 依据 | D-0002 | D-0011 |
| 投递 | 说书人端 | SignalR **定向推送**给该玩家的连接 |

**硬约束**：

1. 请求由服务端发起，客户端**不轮询**、不自行推断轮次。
2. 请求**持久化在服务端**；断线重连后**重新投递**。这是自动重连的内在部分。
3. **内核对请求没有"超时"这个概念，只有"作废原因"**（D-0011 明确暂不设超时）。
   请求一直有效，直到被响应或被上游状态变化作废。
4. 挂起状态**必须可持久化**——不能靠内存里挂着一个长连接等待，否则一重启整局就废了。
5. 无超时的代价必须被对冲：说书人可**强制作废/代填**，说书人端可见"谁在卡着"，每次作废记录原因。
6. **节奏是步骤机的职责，不是 UI 的动画时长**（D-0013）。步骤表按**剧本的完整夜晚顺序表**展开，
   角色不在场 / 已死亡 / 被跳过一律生成**空槽位**并**照样走完时间配额**；
   作废与代填**不得缩短**夜晚。否则"今晚有几个技能位"会通过耗时泄漏给所有人——那是场外信息。

**已落地映射（2026-10-01）**：

| 概念 | 实现（`src/OpenClockTower.Kernel` / `.Application` / `.Server`） |
|---|---|
| 同源选择原语 | `ChoicePrompt`；`DecisionPoint`（说书人）与 `OperationRequest`（玩家）是它的两套投影 |
| 步骤表与槽位 | `StepPlan` / `StepSlot`（`Action` / `Empty` / `Beat` 节拍 / `DawnWait` / `DayWindow` 白天窗口）；空槽位与节拍照样消耗配额，白天窗口不消耗、不自动推进 |
| 挂起 | `StepMachineState` 的 `PendingRequest` / `AwaitingDecision` / `Block`；请求**没有超时字段**（门禁锁死） |
| 推进条件 | `SlotQuotaState`：配额是**最短**时间；自动推进 = 配额走完 **且** 无挂起；强推可越过（D-0014） |
| 事件与重放 | 25 种 `GameEvent`（含 4 种状态账事件与 6 种白天事件）；`StepMachine.Handle` 产事件、`StepMachineFolder` 折叠重建；**账事件可先于任何阶段**（开局分配），此时步骤机保持"尚未开始"；重启 = 重放，恢复 = 重放后替换快照 |
| 开局分配 | `AssignCharactersCommand`：每席一条 `SeatStateChangedEvent`（角色 + 初始生死 = 存活），只允许在首个阶段开始前使用（D-0017 / R-0015） |
| 建表 | `NightPlanBuilder` + `StartNightCommand`：口径进 `StepPlan.Variant`；缺事实显式拒绝，不猜（R-0014 / D-0013） |
| 白天阶段 | `StartDayCommand` 开白天（单 `DayWindow` 槽位）→ `Nominate` / `CastVote` / `CountVotes` → `CloseDay` 处决并走完计划；`ForceAdvance` 兜底立即结束白天（未计票的提名先被要求计票，`docs/backlog/done/day-phase.md` / R-0017） |
| 状态变化归因 | `SeatStateChangedEvent`（座位 + 实际观测维度 + 原因 + 导致方）；说书人视图给 `RecentSeatChanges` / `CurrentSlotActor` / `CurrentSlotContext` / `StepDigest`（每步摘要：状态 + 能力判定 + 作废说明） |
| 玩家可见事件 | 重连补齐只下发 `PlayerEvent` **白名单投影**（公开阶段 + 发给自己的请求 / 响应 / 作废），**绝不下发原始事件流**；**在线推送的覆盖面与它一一对应**（五类事件各有通知，`PlayerNotificationBuilderTests` 锁住） |
| 控制模式 | `ControlMode.Automatic` / `StorytellerTakeover`；接管时节拍器不自动推进，交还后恢复 |
| 作废 | 座位依赖（`SeatDependency`）失效 → 自动作废并写明原因；说书人可强制作废 |
| 推送 | SignalR 定向单播（请求 / 信息 / 作废 / 响应只到当事连接）；阶段开始与**白天变化**是公开信息，广播给**全部已绑定席位**（白天按席位投影后各发一份 `ReceiveDayChanged`）；断线重连 = 快照 + 补齐 + **重投未响应请求**；说书人变更也推送（不需要轮询） |

### 2.8 状态账与效果归因链（D-0015）

> 回答"这一步为什么会变成这样"。它与 §2.7 的步骤机是**同一条事件流上的两个派生视图**（D-0010）。

```text
事件流 ──┬─> StepMachineState   推进到哪一步、在等谁
         └─> GameState（状态账）  谁现在是什么样、身上挂着什么效果、从哪来
```

| 账里的内容 | 承载 |
|---|---|
| 每个席位的已知态（角色 / 阵营 / 生死 / 醉酒 / 中毒） | `SeatStateEntry`，五个维度各带一条 `StateFact`（值 + 原因 + 导致方） |
| 疯狂要求（只由裁定写入，引擎不判定） | `SeatStateEntry.Madnesses`；依据 `rulings.md` R-0003 |
| 持续型效果 | `PersistentEffect`：施加者 / 能力 / 作用对象 / 终止事实 |
| 即时型效果 | `InstantaneousEffect`：已生效即不回滚 |

**折叠规则**（`GameStateMachine`，纯计算）：

| 事件 | 账的变动 |
|---|---|
| `SeatStateChangedEvent` | 只覆盖**本次观测到的维度**，其余维度连同归因一起保留（六维度独立） |
| 同上，且观测到来源死亡 | 该席位施加的持续型效果**立即终止**（原因 `SourceDied`），且不可逆 |
| 同上，且观测到的角色 ≠ 该效果记录的 `SourceCharacter`（施加时的来源角色） | 立即终止（原因 `SourceLostAbility`，依据《重要细节》二-7）。判据是效果自己的"出生条件"，**不依赖"上一次观测到的角色"**——后者在来源角色从未被观测过时会漏判，让早就该终止的效果继续被算成生效 |
| 同上，来源醉酒 / 中毒 | **不终止**，只是 `IsOperative` 变 false；来源恢复即继续生效（同一效果，不是重新施加） |
| `PersistentEffectAppliedEvent` / `InstantaneousEffectAppliedEvent` | 记入效果账（含施加者与作用对象） |
| `PersistentEffectTerminatedEvent` | 只用于折叠推导不出来的终止（如说书人强制作废） |

**边界与失败姿态**：

- 未观测 ≠ 默认值：维度为 null，`IsOperative` 返回 `null`（无法判定），**不猜**；
  `OperativeEffectsOn` 只收"确实生效"的，无法判定的不进结果。
- 效果必须带**完整出生条件**：施加者、能力、作用对象、施加时的来源角色（`SourceCharacter`）。
  缺了来源角色，二-7 的"换角色即失去能力"就无从判定——这是"补全初始条件"在效果上的落点。
- 空事件流 = 空账（"还没观测到任何东西"是合法状态）。
- 顺序损坏（终止不存在的效果、重复终止、重复施加同一条持续型效果、不带任何维度的状态变化、
  同一裁定点重复签发同一条疯狂要求）**显式抛错**。
- **维度翻转不属于账本**（D-0015）：账本只报"哪条效果终止了"，
  把目标的中毒改回健康必须有另一条状态变化事件。

**写入方**：三处——开局分配（`AssignCharactersCommand`：角色 + 存活 + 清醒 + 健康，仅首阶段前）、
说书人上报（`ApplySeatStateCommand` / `GameHub.ReportSeatState`）与**结算引擎**
（角色契约产出效果 / 信息事件，`SettlementReconciler` 产出常驻效果与维度解除事件）。
结算引擎是状态的**推演方**：它读账算生效、产出事件；账本本身仍然只记事实，不替它翻维度（D-0015）。

**已落地映射（2026-10-02）**：

| 概念 | 实现 |
|---|---|
| 状态账 | `GameState`（`Seats` / `PersistentEffects` / `InstantaneousEffects`）+ `SeatStateEntry` |
| 逐维度归因 | `StateFact<T>`（值 / 原因 / 导致方） |
| 效果归因 | `PersistentEffect` / `InstantaneousEffect` 的 `Source` / `Ability` / `Target` / `Termination` |
| 折叠 | `GameStateMachine.Apply` / `Fold`（与 `StepMachine.Apply` 同一套路数） |
| 重建对比 | `GameStateComparer`（五账结构等价，顺序无关）+ `RoomRebuildService`（读全流 → 同源重折两个派生视图 → 三项等价结论 → 原子写快照；失败显式、不返回假"等价"） |
| 房间健康位 | `RoomHealth`（会话态，不进事件流）：恢复 / 重建失败置位（原因 + 首次发生时间），显式重建成功清除；只说书人视图（`StorytellerView.Health`），玩家侧由门禁与投影锁死 |
| 说书人视图 | `StorytellerView.Seats` / `PersistentEffects` / `InstantaneousEffects` / `StepDigest`（每步摘要）；玩家投影里**没有**它（D-0012） |

## 3. 数据流：命令 → 事件 → 投影

```text
玩家/说书人操作 ──> Command（带幂等键 + 客户端序号）
                        │
                    Application 校验
                        │
                     Kernel 推演（确定性；必要时暂停在裁定点）
                        │
                     Event[]（追加写，序号单调递增）
                        │
        ┌───────────────┴───────────────┐
    说书人视图投影                   玩家视图投影（每人一份）
```

- **事件是唯一事实来源**；当前状态是可重建的派生结果。
- **视角投影在服务端强制**：玩家端**根本收不到**越权资料（D-0009）。
- **撤销** = 截断到指定序号后重放，保留审计轨迹，不删除历史。

## 4. 安全模型：零信任（D-0012）

**一条不变量**：客户端送来的一切都不被信任——包括"我是几号玩家""我的角色是什么""我投了谁"。
服务端只信**自己推导出的状态**。客户端发来的身份声明只用于**定位会话**，绝不用于**授权**。

### 4.1 鉴权两层

| 层 | 作用 | 生命周期 |
|---|---|---|
| 会话票据 `SessionTicket` | 证明"你是这一局的哪一名玩家" | 整局有效；重连时重新出示 |
| 私有凭据 `ConnectionCredential` | 绑定到**下发它的那条连接** | 连接建立时下发；重连必须重新出示 |

票据本身**不是**授权凭证：拿到票据不等于拿到视图，视图永远由服务端按当前状态重新投影。

### 4.2 操作的**四道闸**

每个命令进内核之前必须依次通过：

```text
命令 ──> ① 身份闸   你是谁？你在本局是什么身份？
     ──> ② 阶段闸   现在什么阶段？轮到你了吗？这个请求是发给你的吗？
     ──> ③ 合法性闸 你提交的选项，在服务端算出的合法集合里吗？
     ──> ④ 幂等闸   幂等键 + 客户端序号：这是不是重复投递？
     ──> Kernel
```

任何一闸不过：**拒绝、记录、不改状态**。拒绝也要有日志上下文（谁、哪一闸、什么输入）。

**实现顺序（2026-10-01）**：身份 → **幂等** → 阶段 → 合法性。幂等闸提前到阶段闸之前：
重复投递必须返回首次结果，否则阶段闸会把"请求已了结"的重复命令误判成非法。
第 ①③④ 闸的语义不变，只有顺序按实现需要调整——这是唯一一处与本节图顺序不同的地方。

**已落地（2026-10-02）**：

| 环节 | 实现 |
|---|---|
| 连接级凭据 | `ConnectionCredential`（32 字节密码学随机，base64url）；`ConnectionRegistry` 只存 SHA-256 哈希、固定时间比较；Join 成功签发并随 `SeatJoinDto` / `StorytellerJoinDto` 下发，此后**每条命令第一个参数**都是它 |
| 凭据生命周期 | 同席新连接替换旧连接 → 旧连接凭据**立即作废**（TCP 未断也发不出命令）；断开即失效；重连必须重新出示票据（矩阵行 3） |
| 身份解析 | `GameHub.ResolveActor(credential)`：凭据 → 服务端身份（`Player(席位)` / `Storyteller`），客户端声明一律不认；凭据无效在 Server 拒绝 + 审计，**不触达 Application** |
| 四道闸 | 仍在 Application（`CommandGatePipeline`）：身份 → 幂等 → 阶段 → 合法性；玩家凭据调说书人命令由**身份闸**拒绝（`identity.storyteller_only`），不被凭据解析吞掉 |
| 审计 | 两层：Server（凭据闸：连接 id、方法、凭据短指纹、原因，含参数层拒绝）与 Application（gate / code / actor / seat / command）；日志绝不写凭据明文 |
| 并发与路由一致性 | 注册表的签发 / 作废 / 断开在**同一临界区**完成；`Validate` 核对"凭据身份与当前席位路由一致"——防并发抢占残留与"同一连接换席位"的路由分叉（复核发现，2026-10-02） |
| 拒绝回执脱敏 | 阶段闸把"没有请求 / 已了结 / 不是发给你的"统一成 `phase.no_request_for_you`；拒绝回执**不带全局事件序号**——拒绝码与序号都不许当探测他人活动的预言机（D-0013 §5） |
| 前端 | 凭据只存内存（票据才进 `TicketStore`）；命令经 `CommandSender`（连接 + 凭据）发出，组件拿不到裸连接；`display/format.ts` 对长度 / 类型 / 范围做有界化 |
| 取证 | 负向集成套件 `ZeroTrustHostTests`（行 1–6、11 的真宿主反例）＋ 真机装置 `tools/verify-zero-trust.mjs`（篡改客户端直调 Hub、玩家收包扫描、审计日志扫描） |

### 4.3 信息只在**下发方向**校验

- 服务端按接收者投影；**越权信息根本不下发**，不依赖"前端不显示"。
- 反面教材：把整局状态发给所有人、由前端决定显示什么——开发者工具一开就全泄了。
- 验收时**必须验反方向**："不该看见的人确实没看见"（见 `docs/acceptance/AGENTS.md` §4）。

### 4.4 前端把服务端数据当不可信输入

长度、类型、范围都要防御性处理；渲染不插裸 HTML。前端是呈现层，不是安全边界。

### 4.5 什么**不算**漏洞

玩家在自己设备上能看到**自己**的全部信息（含"你被要求疯狂地证明你是 X"）——
这是规则允许的，是设计而非缺陷。零信任防的是**越权**，不是"玩家知道自己的角色"。

## 5. 同步与重连

依据 D-0010：

```text
重连：会话票据 ──> 校验 ──> 快照(序号 N) + 可见事件(本地已知..N] ──> 客户端重建
```

- **快照序号 N 就是客户端的新 watermark**：服务端在锁内读全量事件后按接收者投影，快照与序号同源，
  全局连续性由服务端保证。
- 补齐事件是**白名单投影**（D-0012 §4.3）：他人事件根本不下发，客户端**不得**用事件条数证明序号区间完整
  （否则必然误报，也违反 D-0013 §5 不泄露活动数量）；可见事件只要求**严格递增**且落在 `(本地已知, N]`。
- **在线推送携带事件序号**（票据 `player-information-resync-race`）：定向推送取背书事件的序号；
  白天投影与说书人视图这类"读时状态"取**读取时的序号**。客户端由网关**单一写入**，把快照与推送
  按序号合并后整份交给界面：信息结果按序号并集去重，阶段 / 白天 / 请求按各自字段序号取新。
  **快照序号低于本地已知不是坏包**，而是"推送先到、响应后到"的正常竞态，按字段序号取舍即可
  （此前推送无序号、两个写入者互相覆盖，窗口内的推送会被静默丢弃）。
- **两个水位用途不同**：字段序号可以来自推送（决定字段取舍）；送去 `JoinSeat` 的"本地已知"是
  **事件窗口水位**，只由快照推进——读时推送的序号可能领先于本席真实的事件位置，拿它当已知序号
  会把缺口事件窗口整段截断。快照序号低于**事件窗口水位**则意味着服务端事件流回退
  （数据丢失 / 从旧备份恢复）：客户端清空合并态、以快照为新基线并出诊断（序号会被复用，
  不清空会把新事实当重复丢掉）。
- 说书人视图整份带序号：Join / 刷新响应与推送同属一条序号流，只接受序号不更旧的视图。
- 坏数据不静默：条目不可识别，或可见事件序号越界 / 倒退 / 重复 → 显式失败并停在当前视图，
  **不前进 watermark**、也不采纳这份包（宁可报错，不许"本地先按旧状态继续跑"）。
- 命令携带幂等键，重复提交不产生重复效果；客户端发现自己的视图需要刷新 → **主动请求补齐**。
- **禁止**：延迟窗口、保护期、本地先跑再跟随、新旧同步机制并存。

| 请求无超时 | `OperationRequest` 契约里出现超时 / 时间字段（D-0011 硬约束 3） |
| 玩家投影无进度 | 玩家投影 / 请求 DTO 出现轮次、槽位、进度字段（D-0013 §5） |
| 效果终止带原因 | 内核里出现无参 `Terminate()`——终止必须可归因（票据「说书人上帝视角」第 2 条） |
| 单文件 ≤ 600 行 | 源文件超过 600 行（AGENTS.md「架构硬约束」：超限先拆再改） |
| 演示计划不进生产代码 | `src/` 里出现 `DemoStepPlan` 或同类占位计划（会被误当成规则） |
| 会话票据不承载角色 | `GameSetup` / 会话表出现角色字段（角色分配必须走事件流，D-0017） |
| 行动契约带规则来源 | `INightAction` 实现缺「百科《…》+ 抓取日期」引用 |
| 计划不进 wire | `Contracts` 出现 `StepPlan` / `StepSlot`（客户端不提供计划、也不该看到计划） |
| 玩家端不引用说书人字段 | `web/src/features/player` 与共享 `web/src/services` 里出现 `seats` / `effects` / `causedBy` / `slotIndex` 等说书人专属字段名（D-0018、§4.3） |
| 玩家端只依赖玩家侧模块 | `web/src/features/player` 与共享 `web/src/services` 里出现允许清单之外的 import，或引用说书人专属 DTO 类型名（D-0018） |
| 前端契约镜像对账 | `web/src/contracts/game.ts` 与 `src/OpenClockTower.Contracts/*.cs` 字段名 / 形状 / 必填性不一致，或镜像出现契约里没有的幽灵字段（D-0004、D-0018） |
