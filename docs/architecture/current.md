# 当前架构

> 本页回答一个问题：**这套系统由哪些部分组成，依赖朝哪个方向，以及游戏逻辑为什么能算对。**
> 决策来源见 `docs/decisions/active.md`；术语以 `docs/standard/terminology.md` 为准。

## 1. 分层与依赖方向

依赖只能从上往下。`Kernel` 不认识任何框架、不认识数据库、不认识网络。

```text
        Web (Vue 3 + TS)                     ← 说书人端 / 玩家端，两个视图
              │  HTTP + SignalR
        Server (ASP.NET Core 宿主)            ← 认证、SignalR Hub、EF Core 持久化
              │
        Application (用例编排)                ← 命令/查询、裁定点编排、会话协调
              │
        Rules (梦殒春宵的角色与相克数据)       ← 角色行为实现、剧本定义、相克表
              │
        Kernel (纯规则内核 · 确定性 · 无 IO)   ← 状态、效果生命周期、结算、冲突解析、胜负
```

| 层 | 职责（单一） | 明确**不**做 |
|---|---|---|
| `Kernel` | 状态推演、效果生命周期、结算调度、冲突解析、胜负判定 | IO、时间、随机、日志副作用、持久化 |
| `Rules` | 角色能力的**行为实现**、剧本/角色/相克规则**数据** | 结算顺序的通用规则（属 Kernel） |
| `Application` | 一次"操作"的编排：校验命令 → 产生事件 → 投影视图 | 规则判定本身 |
| `Server` | 宿主、认证、Hub、仓储、快照调度 | 任何领域判断 |
| `Web` | 呈现与输入 | **不承担信息隔离**（隔离在服务端） |

**关键先例**：`Kernel` 通过**接口**声明它需要的外部能力（如"请求一次裁定"），
由上层注入。这样依赖图无环，且内核可以被纯粹地测试。

## 2. 内核领域模型

### 2.1 玩家状态：六个正交维度

依据：百科《重要细节》三——"玩家的状态有：角色、阵营、生死、醉酒、中毒、疯狂"，
且**"状态与玩家绑定，而不与角色绑定"**；"在游戏开始后，玩家的不同状态之间相互独立，互不干涉"。

```text
Seat (玩家席位)
├── Character    角色     ← 会变（角色交换、被创造、复活）
├── Alignment    阵营     ← 会变（阵营转变）；与角色无关
├── Life         生死     ← 存活 / 死亡
├── Drunk        醉酒     ← 醉酒 / 清醒
├── Poisoned     中毒     ← 中毒 / 健康
└── MadnessReq   疯狂要求  ← 只由裁定写入；引擎不判定
```

**硬约束**：这六者**不得有联合约束**。任何形如"当角色变为 X 时顺带清除醉酒"的写法都是 bug——
百科《重要细节》三明确："因其他角色能力而醉酒的玩家角色发生了变化，不会让玩家因此解除醉酒。"

### 2.2 效果生命周期：本项目最容易做错的地方

依据：百科《重要细节》二-3 与三-3。

| | 即时型 `Instantaneous` | 持续型 `Persistent` |
|---|---|---|
| 生效时机 | 立即，改变局面后即结束 | 持续存在，被持续查询 |
| 来源死亡/醉酒/中毒时 | **不回滚**（已经发生过） | **立即终止** |
| 来源恢复时 | 不复活 | **继续生效**（不是"重新施加"） |

**两条必须分开记录的账**：

1. **能力使用账本**（`AbilityUseLedger`）
   一次性能力在**醉酒或中毒期间被使用 = 已浪费**。百科《重要细节》三-3："如果他醉酒或中毒期间
   尝试使用自己的'每局游戏限一次'的能力，他无法在之后再次使用这项能力。使用机会会被浪费。"
   → 因此"是否使用过"与"是否生效过"是**两个独立的布尔量**。

2. **失效账本**（`MalfunctionLedger`）
   记录每一次"能力未正常生效"及其**原因**。这不是调试日志，是**游戏机制**——
   数学家要靠它给出数字。口径尚未逐条核对完，见 `docs/standard/rulings.md` R-0004。

### 2.3 触发类型

百科《角色能力类别总览》列出的是**机制族**，内核按"什么时候被求值"归类：

| 类别 | 求值时机 | 例 |
|---|---|---|
| `NightAction` | 夜晚顺序表调度 | 舞蛇人、筑梦师 |
| `OnDeath` | 某玩家死亡的那一刻 | 守鸦人 |
| `Entry` 进场能力 | 角色被创造/变更后尽快结算 | 痢蛭选宿主 |
| `PublicTrigger` 公开触发能力 | 玩家在白天公开声明 | 猎手 |
| `Retroactive` 回溯型能力 | 先记条件，后结算结果 | 杂耍艺人 |
| `ContinuousDetection` 持续检测型 | 每次被查询时重新计算 | 占卜师（干扰项动态化）、共情者 |
| `LimitedUse` 限次能力 | 正常调度 + 次数约束 | 猎手 |
| `GainAbility` 获得能力 | 改变某玩家的能力来源 | 哲学家 |
| `Interference` 干扰 | 改变其他能力的**生效与否** | 中毒、醉酒、涡流、咖啡师 |

### 2.4 裁定点（DecisionPoint）

> 依据 D-0002：平台只做**记录 + 校验 + 推演**。

每个裁量点是一个**具名契约**：

```text
DecisionPoint
├── Id           稳定标识（进事件流，永不改变）
├── Context      为什么需要决定（涉及谁、哪个能力、哪一步）
├── Options[]    合法选项（引擎算出并校验过的）
├── Preview      每个选项的后果预览（由内核试算得出，不改真实状态）
└── OnNoOption   无合法选项时的行为：跳过 / 自由决定 / 阻塞报警
```

**硬约束**：

- 角色实现**禁止**自己选目标、自己摇随机数、自己决定真假信息——一律走裁定点。
- `OnNoOption` 必须显式声明。依据 `docs/standard/rulings.md` R-0009：占卜师的干扰项要求"任意善良玩家"，
  极端局面下可能无合法选项。禁止抛异常，也禁止静默跳过。
- 裁定点进事件流，因此**可回放、可撤销、可回归测试**。

### 2.5 冲突解析

结算中所有冲突走同一条判定链，顺序是**项目自定口径**（见 `rulings.md` R-0005，尚未获百科确证）：

```text
相克规则  >  不能最大  >  角色能力  >  核心规则
```

- **不能最大**（百科《隐性规则汇总》§2）：一个能力允许、另一个禁止时，**禁止方生效**。
- **角色唯一**（§4）：同一角色同时最多一个在场；能力造成角色变化时不得违反，除非明说（军团等）。
- **死亡串行**（§5）：**不存在同一时刻多名玩家同时死亡**，死亡一律按序逐个发生。
- **过时不候**（§6）：当晚某角色的时机已结算过，之后新出现的该角色当晚不再行动。
- **胜负判定时机**（`rulings.md` R-0008）：一次结算事务内连续产生的死亡**不中途判胜负**，事务提交后统一判定。

### 2.6 结算引擎

```text
夜晚阶段
  ├── 建表：按剧本的夜晚顺序表展开今晚的步骤序列
  ├── 逐步推进：每一步 → 求值触发条件 → 需要裁定则暂停等说书人
  ├── 允许插入：OnDeath / Entry 触发的步骤插到当前位置
  └── 束：结算事务提交 → 统一判定胜负 → 产出事件
白天阶段
  ├── 提名（同日每人一次 / 被提名一次）
  ├── 投票（死亡玩家仅剩一次机会，且需有投票标记）
  ├── 判定：票数最多 且 ≥ 存活人数一半；与他人并列最多则均不处决
  └── 处决（处决 ≠ 死亡）
```

### 2.7 步骤机与操作请求（D-0011）

"自动步骤系统"不是一个 UI 特性，它是内核里的一台状态机。

```text
StepMachine（步骤机）
├── 当前阶段：首夜 / 其他夜晚 / 白天 / 结算中
├── 当前步骤：夜晚顺序表上的第 k 步
├── 挂起点：本步是否在等某个请求被响应
└── 产出：操作请求 / 裁定点 / 事件
```

**两个受众不同的原语，同源不同投影**：

| | `DecisionPoint` 裁定点 | `OperationRequest` 操作请求 |
|---|---|---|
| 问谁 | **说书人** | **玩家** |
| 例子 | "占卜师的干扰项选谁？" | "1 号，请选择两名玩家查验" |
| 依据 | D-0002 | D-0011 |
| 投递 | 说书人端 | SignalR **定向推送**给该玩家的连接 |

**硬约束**：

1. 请求由服务端发起，客户端**不轮询**、不自行推断轮次。
2. 请求**持久化在服务端**；断线重连后**重新投递**。这是自动重连的内在部分。
3. **内核对请求没有"超时"这个概念，只有"作废原因"**（D-0011 明确暂不设超时）。
   请求一直有效，直到被响应或被上游状态变化作废。
4. 挂起状态**必须可持久化**——不能靠内存里挂着一个长连接等待，否则一重启整局就废了。
5. 无超时的代价必须被对冲：说书人可**强制作废/代填**，说书人端可见"谁在卡着"，每次作废记录原因。
6. **节奏是步骤机的职责，不是 UI 的动画时长**（D-0013）。步骤表按**剧本的完整夜晚顺序表**展开，
   角色不在场 / 已死亡 / 被跳过一律生成**空槽位**并**照样走完时间配额**；
   作废与代填**不得缩短**夜晚。否则"今晚有几个技能位"会通过耗时泄漏给所有人——那是场外信息。

## 3. 数据流：命令 → 事件 → 投影

```text
玩家/说书人操作 ──> Command（带幂等键 + 客户端序号）
                        │
                    Application 校验
                        │
                     Kernel 推演（确定性；必要时暂停在裁定点）
                        │
                     Event[]（追加写，序号单调递增）
                        │
        ┌───────────────┴───────────────┐
    说书人视图投影                   玩家视图投影（每人一份）
```

- **事件是唯一事实来源**；当前状态是可重建的派生结果。
- **视角投影在服务端强制**：玩家端**根本收不到**越权资料（D-0009）。
- **撤销** = 截断到指定序号后重放，保留审计轨迹，不删除历史。

## 4. 安全模型：零信任（D-0012）

**一条不变量**：客户端送来的一切都不被信任——包括"我是几号玩家""我的角色是什么""我投了谁"。
服务端只信**自己推导出的状态**。客户端发来的身份声明只用于**定位会话**，绝不用于**授权**。

### 4.1 鉴权两层

| 层 | 作用 | 生命周期 |
|---|---|---|
| 会话票据 `SessionTicket` | 证明"你是这一局的哪一名玩家" | 整局有效；重连时重新出示 |
| 私有凭据 `ConnectionCredential` | 绑定到**下发它的那条连接** | 连接建立时下发；重连必须重新出示 |

票据本身**不是**授权凭证：拿到票据不等于拿到视图，视图永远由服务端按当前状态重新投影。

### 4.2 操作的**四道闸**

每个命令进内核之前必须依次通过：

```text
命令 ──> ① 身份闸   你是谁？你在本局是什么身份？
     ──> ② 阶段闸   现在什么阶段？轮到你了吗？这个请求是发给你的吗？
     ──> ③ 合法性闸 你提交的选项，在服务端算出的合法集合里吗？
     ──> ④ 幂等闸   幂等键 + 客户端序号：这是不是重复投递？
     ──> Kernel
```

任何一闸不过：**拒绝、记录、不改状态**。拒绝也要有日志上下文（谁、哪一闸、什么输入）。

### 4.3 信息只在**下发方向**校验

- 服务端按接收者投影；**越权信息根本不下发**，不依赖"前端不显示"。
- 反面教材：把整局状态发给所有人、由前端决定显示什么——开发者工具一开就全泄了。
- 验收时**必须验反方向**："不该看见的人确实没看见"（见 `docs/acceptance/AGENTS.md` §4）。

### 4.4 前端把服务端数据当不可信输入

长度、类型、范围都要防御性处理；渲染不插裸 HTML。前端是呈现层，不是安全边界。

### 4.5 什么**不算**漏洞

玩家在自己设备上能看到**自己**的全部信息（含"你被要求疯狂地证明你是 X"）——
这是规则允许的，是设计而非缺陷。零信任防的是**越权**，不是"玩家知道自己的角色"。

## 5. 同步与重连

依据 D-0010：

```text
重连：会话票据 ──> 校验 ──> 快照(序号 N) + 事件(N..现在] ──> 客户端重建
```

- 命令携带幂等键，重复提交不产生重复效果。
- 客户端发现事件序号缺口 → **主动请求补齐**，绝不"先按本地状态继续跑"。
- **禁止**：延迟窗口、保护期、本地先跑再跟随、新旧同步机制并存。
