## 要解决的问题

需求方 2026-10-07 当面定调了三条口径，逐条如下（**已拍板，不再讨论**）：

1. **入座必须登录**：删掉"没有账号、只凭席位票据入座"这条路。登录系统是唯一入口，不做第二套免登录路径。
   匿名连接仍然存在（没入座的连接），只是**不能入座**。
2. **席位票据改作邀请码**：桌分**公开桌**（大厅点空席位就坐）与**邀请制桌**（必须凭邀请码）。
   邀请码就是今天那串「桌标识:席位票据」，**协议不用改**。
3. **邀请制桌在大厅里仍然列出**，标「邀请制」，点不动（不隐藏）。
4. **说书人随时能改这个状态，局内实时生效**：切换后推给该桌的所有连接（说书人视图 + 在场玩家），
   不刷新、不重连就变。
5. **开局即关闭自助入座**（= 一局开始后自动进入邀请制）；迟到的旅行者由说书人发邀请码进来。
6. **正名**：库里那一列 `IsLocked` → `IsInviteOnly`（**库结构 v3**）；代码、术语、文案、门禁一齐对齐"邀请制"。
7. **旅行者离场**：旅行者**向说书人提出离开申请** → 说书人**批准后执行**（座位离场）；
   说书人**也保留直接移出**的权限。走"玩家发起 → 说书人裁定"那条现成的形态
   （参考艺术家提问的状态机：asked → resolved/closed 进事件流、可回放），**不要做成自助离开**。

### 开工前清点出来的两个现状（本轮不再重新发现）

- **"邀请制"这个能力今天已经有一半**：说书人的"锁桌"（`SetTableLock` → `Games.IsLocked`）实际效果是
  "自助入座被拒、持票据者照进"——这正好是邀请制的语义。审计当年把"锁桌没拦住票据入座"记成缺陷
  （`G-A4-2`，Medium），**按新模型那不是缺陷而是设计**：本批把它的收口方式改成
  "正名（`IsInviteOnly`）+ 改口径 + 补一条正向判据（持码者进得来）"，**不再去补那道闸**。
- **真正缺的闸在"开局之后"，而且今天只拦在前端**：自助入座（`SeatJoinCoordinator.JoinBySeatAsync`）
  只判 `IsLocked`，**从不判"已开局"**；前端在开局后不显示座位按钮，服务端照样接受。
  这正是项目铁律"前端不显示按钮不算鉴权"的反面案例，本批在服务端补上。

### 本批的代价（如实记下，不在本批清零）

邀请码仍然是"明文落库、不过期、不轮换"的那串票据（审计 `G-A2-2`，High，**本批不清零**）——
本批只是把用它的**人**收窄（必须登录、且只出现在邀请制桌与旅行者路径）。
要真正收口得另开一条（给码加有效期 + 轮换）。

## 目标形态

| 面 | 今天 | 本批之后 |

| 自助入座闸 | 只看 `IsLocked`（开局不拦，纯前端） | 邀请制 **或** 已开局 → 拒；本人已认领的那一席仍可回（回到座位不是自助入座） |

## 决定与依据

- **D-0037**（本批新增）记下口径：账号是唯一入座入口 · 公开 / 邀请制两种桌 · 开局即关自助入座 ·
  邀请码沿用席位票据（明文、不过期、不轮换，`G-A2-2` 本批不清零）· 离场申请走"玩家发起 → 说书人裁定"。
- 规则依据：百科《旅行者》· 2026-10-04 抓取（加入 / 离开流程）+ `rulings.md` R-0044 第 6 条
  （离场：席位与票据保留，不再计入任何人数口径）。本批不改这两条口径，只改**谁来发起**。
- 审计 `G-A4-2`（锁桌不拦票据入座）**按新模型结案**：不是缺陷，是邀请制的语义；收口方式改为
  "正名 + 改口径 + 补正向判据（持码者进得来）"。`G-A2-2`（邀请码明文 / 不过期 / 不轮换）标注为
  **本批不收窄，另开一条**。
- 库结构 v3 的**可逆性**：`ALTER TABLE Games RENAME COLUMN IsLocked TO IsInviteOnly;` 一句，
  回滚 = 反向改名 + 把 `user_version` 改回 2（口径写进部署文档 §9.3）。
- 离场申请**放进事件流**（而不是只在内存里挂一个请求）：可回放、可审计，且服务端重启后仍成立。
  它与"操作请求"的区别是**方向相反**——那是服务端问玩家，这是玩家问说书人。

## 本批明确不做 / 留作残余

- **G-A2-2**（邀请码明文落库、不过期、不轮换，High）：本批只收窄**用它的谁**，凭据形态没动。
- **`StateLedger` 的等价比较仍有缺口**：`GameStateComparer` 这轮补了 `DepartureRequests`，
  但 `Activity` / `VigormortisKills` 仍未参与"重建后账一致"的比对（历史缺口，与本批无关，
  登记在此避免下次重新发现）。
- **开局闸的呈现**仍靠 `started || inviteOnly` 两条事实在前端合成一句「邀请制」；服务端各判各的。
