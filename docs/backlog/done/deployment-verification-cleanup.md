# 部署验证留下的测试桌与陈旧产物：清理

- Status: Done（2026-10-06 当场清掉；留下的"部署流程要顺手清"已写进通用说明）
- Priority: Medium
- Depends on: 无

## 要解决的问题

多桌形态的**部署验证**（真机探针 + 真浏览器）在服务器上留下了可见的垃圾：

1. **多张测试桌**：`甲桌…` / `乙桌…` / `界面桌…` 若干张，全是探针与浏览器用例建的，
   默认桌 `default` 之外都不该留着。它们会**直接出现在玩家端的大厅列表里**——
   用户打开页面看到一屏测试桌，等于把验证痕迹当成了界面。
2. **一批测试账号**：`<运维账号>`（真实管理员，保留）、`bob…` / `e2e…` 等注册用例的账号。
3. **`wwwroot/assets/` 里的陈旧产物**：前端每次构建换文件名，服务器上累积了 12 个 js/css。
   构建时的清理由 csproj 的 `CopyFrontendToWwwroot` 负责，但那是**本机输出目录**的清理；
   服务器上被 `tar` 覆盖式解压时，旧文件不会被删（tar 只覆盖同名、不删多余）。
4. `/root` 下的中转文件（`oct-linux.tar.gz` / `oct-server.tar.gz` / `diag.sql` / `tickets.txt`）。

## 为什么单独立票而不是顺手做掉

- 删除**桌**等于删数据（虽然都是测试数据），要有明确的"删哪些、留哪些"判据；
- 服务器上还留着 `default` 桌与 `<运维账号>` 账号——那是真实可用的，不能一起删；
- 清理动作要可复核：先列候选（哪些桌、哪些文件），再逐项删，再看一遍。

## 验收矩阵

| # | 场景 | 期望 |
|---|---|---|
| 1 | 大厅列表 | 只剩用户真正要用的桌（当前是 `default`） |
| 2 | 账号 | 保留真实管理员；测试账号一并清掉（或明确保留并说明原因） |
| 3 | `wwwroot/assets` | 只剩 `index.html` 当前引用的那一份 js/css |
| 4 | `/root` 中转文件 | 清空（部署脚本随时能重新生成） |
| 5 | 清理后 | 服务仍 active、首页 200、大厅可打开 |

## 决定与依据

- **不许用递归删除**：按 `AGENTS.md` 的删除纪律，逐层"查看 → 批量删除 → 回看"；
  桌与账号在库内，先用 SQL 列出候选再删（并且只删"不在保留清单里"的那些）。
- 顺带把"部署脚本要不要清理服务器上的陈旧产物"这件事定下来：若定"要"，
  就在 `deploy-prepare.mjs` 的部署说明里加一条 `rm -f wwwroot/assets/*` 前置，
  否则每部署一次就多一份垃圾（本次已累积 12 个）。

## 清理结果（2026-10-06）

按"先列候选 → 逐项删 → 回看"做完，逐条对上验收矩阵：

| # | 场景 | 结果 |
|---|---|---|
| 1 | 大厅列表 | 7 张测试桌 → 只剩 `default` |
| 2 | 账号 | 12 个 → 只剩真实管理员 `<运维账号>`（11 个 `bob…` / `e2e…` 测试账号已删） |
| 3 | `wwwroot/assets` | 13 份 → 只剩 `index.html` 当前引用的那一份 js + css（引用完好已复核） |
| 4 | `/root` 中转文件 | 6 个（两个 50MB 包 / 两个 sql / conf / service）→ 清空；**同机其他项目目录一个未动** |
| 5 | 清理后 | 服务 `active`、首页 200、`/healthz` 正常 |

**流程改进（已落地）**：第 3 条不是"手滑留下的"，而是**流程本身缺一步**——
tar 覆盖式解压不删旧文件，而前端产物每次都换哈希文件名。
已在 `docs/operations/deploy.md` §7 与 `deploy-prepare.mjs` 的输出里加上
`rm -f <APP_DIR>/wwwroot/assets/*` 这一步，并把成因写清楚。

## 测试卫生（清理本机时顺带咬出来的，比部署垃圾更值得记）

清理 `%TEMP%` 时发现**成片残渣**，逐类定位到根因：

| 残渣 | 数量 | 根因 | 处置 |
|---|---|---|---|
| `oct-lobby-*` 目录 | 87 | `LobbyHostTests` 的 `Dispose` 没清 SQLite 连接池，库文件删不掉 | **已修**（加 `ClearAllPools`，并验证"跑完不新增"） |
| `oct-multitable-*` 目录 | 25 | 早期版本的 `MultiTableIsolationTests`（后改为纯内存，不再产生） | 已清，无需改 |
| `oct-test-*.db` 等 | 250+ | 同上；测试进程被中断 / 句柄未释放时的残留 | 已清 |
| `oct-<名字>-<guid>.db` | 17 | `TestServerHost` 在 `deleteDatabaseOnDispose: false` 时**故意不删**（重启类用例共享库） | 见下 |

**试过但撤回的方案（教训）**：给 `TestServerHost` 加"同一库文件引用计数，最后一个使用者删"。
结果是 **19 条重启类用例当场变红**——重启用例是"第一个宿主 dispose → 第二个宿主起来"，
两者**并非同时在场**，引用计数在中间归零，第二个宿主起来时库已经没了。

> 这类"看起来更聪明"的清理逻辑，必须先问"生命周期真的是重叠的吗"。
> 撤回后测试恢复全绿；那 17 个具名库改由收尾清理，**不拿测试正确性换清洁**。

**同族检查与结论**：`StaticHostingTests` 早先已修过同一个连接池问题；`LobbyHostTests` /
`MultiTableHostTests` 是新写的，漏了。**新写涉及临时库的测试类，必须一并清池**——
这条作为新增测试时的检查项。
