# 白天阶段：提名 / 投票 / 处决

- Status: Done
- Priority: High
- Depends on: 自动步骤机与操作请求（`done/operation-request-step-machine.md`）；结算引擎（`done/settlement-engine.md`）；下游被卡：零信任票行 5（`done/zero-trust-security-model.md`，批次 E9 已解锁）

## 要解决的问题

平台已经有夜晚与步骤机，但**白天阶段完全空白**：`GamePhase.Day` 只是枚举里的一项，
没有任何提名 / 投票 / 处决流程。后果：

1. 一局游戏第一夜走完后无法继续——说书人没有"开白天"入口，玩家不能提名、投票、被处决；
2. 零信任票行 5「玩家在白天提交夜间行动」没有场景载体，按验收规程只能留在 `review/`；
3. 卖花女孩 / 城镇公告员这类"白天事实 → 夜晚信息"的角色没有事实来源（本票先把事实记全）。

## 实施方案（2026-10-02 架构审视）

### 1. 现状与缺口

- 现状：`StepMachine` 按 `StepPlan` 槽位推进（配额是夜晚时序防泄漏的机制，D-0013）；
  命令走 `CommandGatePipeline` 四道闸；`GameSession` 串行编排；事件流是唯一事实来源（D-0010）；
  `StepMachineState` 与 `GameState` 是同一条事件流上的两个派生视图。
- 缺口：白天没有任何状态、事件、命令、投影与界面；`CommandGatePipeline` 的“阶段闸”只能区分
  “有没有挂起请求”，没有“现在是白天”的语境。

### 2. 目标域模型（白天）

- **阶段**：`StepPlan { Phase = Day, Slots = [DayWindow] }`。`DayWindow` 是新槽位类型：
  **不走配额、不自动推进**；白天只能被说书人的 `CloseDay` 结束（`ForceAdvance` 仍是兜底：
  立即结束白天、不产生处决）。
- **白天账** `DayState`（存放在 `StepMachineState.Day`，随快照持久化、随事件折叠、跨阶段保留）：
  - `Days`：按天记录（当天提名、票面、计票结果、即将被处决、实际处决、是否已关闭）；
  - 死亡玩家已消耗的投票权（跨天保留——它是"死后仅剩一次"的全局次数）；
  - 当天的"每人一次提名 / 每人一次被提名"由当天记录派生。
- **事件**（进同一条事件流，可重放）：`DayStartedEvent`、`NominationMadeEvent`、
  `VoteCastEvent`、`VoteCountedEvent`、`ExecutedEvent`、`DayClosedEvent`。
  处决与死亡**分开记录**：`ExecutedEvent` 记"被处决"这一事实，
  `SeatStateChangedEvent { Life = Dead, Reason = day.execution }` 记死亡结果（本票没有免死角色，
  默认两者同时产生；事件分离为后续"被处决但不死"留位）。
- **输入**：`NominateInput` / `CastVoteInput` / `CountVotesInput` / `CloseDayInput`；
  开白天走与开夜同形的通路（服务端建计划，客户端不提供计划）。
- **计票**：`CountVotesInput` 时对当前开放提名的票面取快照，按机制清点 4–7 算：
  `votes = 票面中投赞成的人数`（存活者不限次数、死亡者消耗票权），
  成功条件 `votes*2 ≥ 存活人数 && votes ≥ 1 && 严格最多`；结果写入 `VoteCountedEvent`
  （含最终票数与投票者名单，供卖花女孩 / 城镇公告员日后读取）。

### 3. 边界与依赖方向

- **Kernel**：白天规则（提名 / 投票 / 计票 / 处决）纯计算；生死、存活人数来自状态账
  （`SettlementContext.State`），观测不齐就拒绝整条命令（不猜，D-0015）。
- **Application**：五条新命令 + 四道闸扩展（身份 / 阶段）+ 审计 + 幂等回执。
- **Server**：白天是**公开信息**（提名、票、处决全员可见）——广播给全部已绑定席位；
  说书人视图给完整票面与资格，玩家视图给公开事实与"我能做什么"。
- **Web**：说书人白天控制台（开白天 / 计票 / 结束并处决 / 当前状态），玩家端白天操作区
  （提名 / 投票 / 公开结果 / 即将被处决）。
- **Rules**：白天角色契约目录（`DayActions`，本票为空目录 + 显式拒绝），
  未实现且与白天相关的角色在场 → `StartDay` 拒绝（同族于夜晚 `plan.contract_missing`）。

### 4. 平台化口径（登记 `rulings.md` R-0017）

- 在线没有"说书人绕圈逐个计票"的物理过程：被提名后进入**投票开放窗口**，说书人决定何时计票；
  窗口内可改票，**计票时以快照为准**；死亡玩家的票权在计票时消耗。
- 辩护时长与"最后一次提名"由说书人掌握，平台不设自动计时（与 D-0011 无超时一致）。
- 白天不走 D-0013 的恒定配额节奏：那条是夜晚时序防泄漏；白天的提名与投票本身就是公开信息。

### 5. 验收矩阵

| # | 场景 | 期望 | 依据 |
|---|---|---|---|
| 1 | 首夜走完后开白天 / 没有夜晚先行的开白天 | 前者受理且阶段为白天；后者被拒 | 机制清点 1 |
| 2 | 提名资格与限制 | 仅存活者可提名；同日每人一次发起、一次被提名；同一时间只能一项；死亡者可被提名；违规被拒且状态不变 | 机制清点 2 |
| 3 | 投票资格 | 存活者每天可投任意多项；死亡者只算一次且计票后消耗；被提名者可投自己；对已计票 / 不存在的提名投票被拒 | 机制清点 4 |
| 4 | 计票判定 | 严格最多 + ≥ 存活一半 + ≥1 才进入「即将被处决」；平票全部取消；后来者须超过打平票数；计票后不因死亡等变化重判 | 机制清点 5–7 |
| 5 | 处决 | 提名阶段结束处决当前「即将被处决」者；每白天一次；无人够票则无处决；处决事件与死亡事件都进流；处决后白天结束 | 机制清点 8–9 |
| 6 | 白天 → 夜晚 | 白天结束后可开下一夜；白天进行中开夜被拒 | 机制清点 1 |
| 7 | 视角 | 公开事实对全体玩家**逐席位一致**（只有自己的权限位不同）；窗口期内票面公开是 R-0017 第 5 条登记的口径（线下举手本来就人人可见）；说书人视图含完整票面与资格；玩家视图不含说书人专属字段（门禁 + 运行时投影用例） | D-0012 §4.3；R-0017 第 5 条；验收规程 §4 |
| 8 | 零信任行 5 | 白天提交夜间行动 → 阶段闸拒绝（拒绝码 + 不泄露 + 状态不变 + 审计） | `done/zero-trust-security-model.md` 行 5（批次 E9 通过） |
| 9 | 重启 / 重连 | 白天进行中重启后白天账与在场状态恢复（集成用例）；玩家重连 / 补齐拿到白天快照（E9 装置的重连断言） | D-0010 |
| 10 | 白天角色边界 | 未实现契约且与白天相关的角色在场 → 开白天显式拒绝（不静默跳过） | 架构 §2.6 同族 |

### 6. 不做（本票边界）

- **胜败判定与游戏结束**（涡流"无人被处决"、镜像双子"善良双子被处决"、呆瓜选择等）另立票；
- **白天相关角色能力实现**随角色分批实现（本票只保证"显式拒绝"，不静默跳过）；
- 旅行者 / 流放（R-0007 待需求方决定；首版花名册不含旅行者）；
- 自动计时 / 超时（D-0011 明确无超时；辩护期与计票时点由说书人掌握）。
