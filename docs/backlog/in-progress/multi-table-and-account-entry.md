# 多桌并行 + 账号即入场凭据（改造方案）

- Status: In progress
- Priority: High
- Depends on: 无（D-0021 账号已落地，本票在它之上扩展）

## 要解决的问题

用户视角，两条都是硬伤：

1. **账号系统形同虚设**：注册 / 登录 / 改名在后端与玩家端都存在，但提示是
   "凭票据加入即可认领席位"——**账号不能用来进门**。玩家必须先从说书人那里拿到一串票据
   （`seat-1-…`）才能进入任何一桌，这等于"没有账号系统"。
2. **只允许一桌**：`GameId` 在宿主里是**注入的单例**（`Program.cs` 注入 `new GameId("default")`），
   `Games` 表只有一行，`GameSession` 与 `SeatNameDirectory` 都是进程级单例。
   想同时开两桌只能"另起进程 + 另给端口 + 另给库文件"。

## 现状事实（复核过，不是推测）

| 关注点 | 现状 | 对改造的含义 |
|---|---|---|
| `GameId` 的归属 | Server 层注入单例；`GameHub` / `SeatJoinCoordinator` / `ReplayQueryService` / `HubJoinFlow` 各持一份 | 必须把"当前是哪一局"从**注入常量**改成**按请求解析** |
| 存储层 | `EfGameStore` / `EfGameCatalog` / `EfSeatBindingStore` 的方法**全都已按 GameId 过滤**；`Events` 主键就是 `(GameId, Sequence)` | **隔离已经天然成立**，不用改表结构 |
| `GameSession` | 单例；自己持有 `GameId` 字段并全程用于日志与存储 | 改成"一局一个实例"，由注册表按需创建 |
| `SeatNameDirectory` | **进程级单例**，持有"席位 → 账号 + 玩家名"读模型 | 必须变成**每局一份**（否则两桌会互相看到对方的席位名） |
| 账号 | `Users` 表全局；`SeatBindings` 主键 `(GameId, Seat)` 与索引 `(GameId, AccountId)` | 账号本就跨局（正确）；**席位绑定按局隔离已经成立** |
| 入座路径 | 必须出示席位票据；账号只用于"认领" | 需要新增"账号直接入场"的路径 |
| 通知 | `NotificationDispatcher` 向"本局在线连接"推送 | 需要按局分流 |

**结论**：隔离的地基是对的（存储与绑定都按局分），真正要动的是**DI 的生命周期**
（把"局"从进程级单例降为按 GameId 解析的实例）与**入座/入场模型**。

## 决定与依据

- 单进程多局而非多实例：依据 D-0005 的规模约束，且用户明确要"多桌并行"而非"多机部署"。
- 账号即凭据：D-0021 已建立账号体系与按局隔离的席位绑定，本票只是把"入场"这一步接上去。
- 席位票据保留：D-0021 的游客路径与"换设备兜底"仍有用，废除会丢能力。
- 隔离的判据按 `docs/acceptance/AGENTS.md` §4 的"**不该看见的人确实没看见**"来写（行 8）。

### 第四阶段：开桌权限与说书人身份分离（本轮）

需求方当面指出：把"谁能开桌"定成"只有管理员"而开桌者自动成为说书人，等于**只有管理员能当说书人**——
说书人是玩这一局的角色，不是系统权限。改动：

- `GameServerOptions.AllowPlayerTables`（默认 **true**）：部署级开关，放开 = 任何登录账号都能开桌；
  配 `GameServer__AllowPlayerTables=false` 收口为"只有运维身份能开"（否则关闭后没人开得出第一桌）。
- 新增 `TableCreationPolicy`：只回答"这个账号现在能不能开桌"，与"是不是这一桌的说书人"彻底分开。
- `AdminDirectory.IsAdmin` → `IsOperator`，删掉无人使用的 `HasAnyAdmin`；语义收窄为部署级运维身份。
- `AccountDto.IsAdmin` → `CanCreateTable`；`LobbyCreateResultDto` 结果码 `not_admin` → `not_allowed`，
  且拒绝文案区分"未登录"（`invalid_session`）与"本服不开放自助开桌"（`not_allowed`）。
- 前端：开桌区对所有人可见（去掉"你是管理员"文案），登录后按钮可用性跟 `canCreateTable` 走；
  开桌成功后票据**自动填进输入框**，点「加入」即进主持台（原来要手动抄一串再粘回去）。
- `LobbyHostTests` 重写为九条，核心那条是"**普通账号（无任何名单）开桌成功 → 拿票据真的锁了一次桌**，
  且锁的是他开的那一桌、默认桌没被锁"——票据 → 说书人身份 → 作用在他那一桌，一次闭环。

## 中途放弃的接线方式（教训，别再走一遍）

第一轮尝试把 `Program.cs` 里的单例直接指向"注册表中默认桌的那一份"：

```csharp
builder.Services.AddSingleton(provider => provider.GetRequiredService<GameRegistry>()
    .GetOrCreateAsync(provider.GetRequiredService<GameId>(), CancellationToken.None)
    .GetAwaiter().GetResult()   // ← 问题在这
    .Session);
```

- **结果**：集成用例从 19 红涨到 175 红，随即整体回滚。
- **根因**：DI 工厂里**同步等待异步初始化**（`GetOrCreateAsync` 内含事件流重放 + 库读取），
  解析时机又早于 `GameBootstrapHostedService` 的建库/补列，等于在"库还没准备好"时阻塞等待。
- **结论**：正确的接线是让**消费方按调用接收实例**（`GameHub` 已经这么改了：
  `GameAsync()` 解析一次并记住），而**不是**在 DI 图里把单例重定向到异步组合根。
- **另一条教训**：改造期**不要留"两份事实"**（旧单例读模型 + 每局读模型）——
  实测它会以"认领时更新的那份、与投影读取的那份不是同一个对象"的形式让 81 条用例变红，
  而且红的原因与表象（缺玩家名）相隔很远，极难定位。要迁移就一次迁完。
