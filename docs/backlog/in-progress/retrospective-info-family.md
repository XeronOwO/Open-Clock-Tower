## 要解决的问题

《梦殒春宵》剩下来的镇民里，有三个是同一形态的**记录读者**：除首夜外每夜被唤醒，读「已经发生
的事」，由说书人给出「是 / 否」或一个数字。现在它们**在首版里根本走不到**：

1. 夜晚顺序表上各有行动格（`dreamer → flowergirl → town-crier → oracle → seamstress`），
   但没有结算契约——角色在场时，进入那一格会被步骤机按「在表上却没有契约」显式阻塞；
2. 即便补上契约，也没有可读的事实：白天账记的是**席位**（谁提名、谁举手），而规则要的是
   **那一刻的角色**——百科《卖花女孩》规则细节 4 明确「原恶魔投票之后恶魔换了人，
   卖花女孩仍然检测到**原恶魔**投过票」，用夜晚时刻的当前角色去查会答错；
3. 夜间裁定提示 / 能力结算 / 建表三条上下文都只拿 `GameState`，白天账（`DayState`）
   住在步骤机视图里，读不到。

## 决定与依据

- **白天事实的「时刻快照」**：`NominationMadeEvent` / `VoteCastEvent` 各带一个
  「动作发生时的角色」字段（未观测为 null，不写成默认值），由白天账折叠成
  「提名者角色」与「投票动作表」。理由：恶魔 / 爪牙的身份会在夜里换人
  （麻脸巫婆 / 舞蛇人 / 理发师 / 说书人手工上报），而规则要的是**动作当时**的身份；
  快照进事件流后重放、重启、重建三条路径都得到同一答案（D-0010）。
- **撤回口径（R-0037）**：在线投票窗口内可反复改票（R-0017），线下的「举手」没有对应动作。
  平台取**曾投赞成即记**——撤回不撤销已发生的举手；这是「提醒标记」的在线等价物，
  最终信息仍由说书人给出（D-0002），推演只是提示。
- **白天账入夜的三条路径同源**：建表（`NightPlanRequest` → 提示）、入槽提示重建
  （`SlotPromptRequest` → 提示）、结算（`AbilityResolutionContext`）都把**最近一个白天的账目**
  带进去；三处取同一个 `StepMachineState.Day` 的末条记录，避免「建表看得到、重建看不到」的分叉。
  与 `DaysStarted` / `PitHagNightActive` / `FangGuInfectionConsumed` 同族（步骤机事实按需送进契约）。
- **计数基准（神谕者）**：数**当前账**的「死亡且邪恶」——她排在恶魔之后（顺序表），
  当夜死亡已记账；百科《神谕者》4 要求按魔典上当前阵营（倒置标记）计算，而不是初始阵营。
- **平台边界**：三个角色都只**推演 + 记录**，信息内容由说书人给出（D-0002 同数学家）；
  首夜不开格由顺序表自然满足，不做额外特判。
- **不新增前端面**：裁定点与信息结果复用既有控件（本票无 `web/` 源码改动）。

## 残余（收尾时如实登记）

- 旅行者 / 流放不在首版（R-0007），因此「赞成流放」这类非提名举手不会进账——
  与《卖花女孩》3 的例外天然一致（平台只记提名投票）。
- 卖花女孩「忘记时问恶魔本人」的说书人补救流程（《卖花女孩》8）是线下动作，平台不承载。
