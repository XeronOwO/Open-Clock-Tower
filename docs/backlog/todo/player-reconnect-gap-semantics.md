# 玩家重连「补齐缺口」判据与白名单投影不一致

- Status: Todo
- Priority: Medium
- Depends on: 玩家端视图新鲜度（`done/player-view-freshness.md`）；重连语义（D-0010）

## 要解决的问题

玩家重连 = 服务端**快照** + "从已知序号起的**可见事件**（白名单投影）"。但
`web/src/services/playerGateway.ts` 的 `applyBundle` 要求
`bundle.events.length === bundle.sequence - knownSequence`（事件条数必须逐条覆盖整个序号区间），
而服务端 `PlayerEventProjection.ForSeat` 对不在白名单里的事件返回 null、
`GameSession.GetReconnectBundleAsync` 只收集非 null——于是只要区间里有任何"玩家看不到"的事件，计数必然不等：

- 玩家页出现假告警："重连补齐有缺口：本地已知 0，快照 198 应补 198 条事件，实际收到 4 条"
  （批次 E7 第 11 步探针在修复后的玩家页实测）；
- `lastSequence` 停在旧值：之后每次 resync 都会重新拉全量可见事件，而不是只拉尾差；
- 说书人侧的"补齐完整"结论也被同一个错误判据污染。

设计上两者不可能同时成立：白名单投影（D-0012 §4.3：他人信息根本不下发）加上
D-0013 §5（不泄露"发生过几件事"），客户端就无法用**条数**证明序号连续；
E4 残余事项里"缺口事件只为证明序号连续"的口径与白名单相冲，需要在本票修正。

## 要做的事

1. 客户端判据改为**快照权威**：可见事件只需严格递增、序号落在 `(knownSequence, bundle.sequence]`；
   快照序号即新 watermark（服务端已读全量事件后再投影，连续性由服务端保证）。
2. 序号越界 / 倒退 / 重复仍显式诊断并且不前进 watermark（保留"宁可报错、不静默继续"）。
3. 更新 `web/src/services/playerGateway.spec.ts`；把重连补包的实际语义写进架构 §5 与
   `done/player-view-freshness.md` 残余事项的后续口径（不改历史结论，只补"后续修正"指针）。
4. 真机：断线窗口内制造隐藏事件（他人请求 / 状态变化）→ 重连后玩家页**不再**出现
   "应补 N 实际 M"假告警，且可见事件与信息结果仍按快照正确呈现。

## 验收矩阵

| # | 场景 | 期望 | 依据 |
|---|---|---|---|
| 1 | 掉线期间存在隐藏事件 | 重连无假告警，watermark 前进到快照序号 | D-0010 / D-0012 §4.3 |
| 2 | 可见事件序号越界 / 倒退 / 重复 | 显式诊断，watermark 不前进 | E4 口径（宁可报错，不静默继续） |
| 3 | 补齐包可见性 | 仍只含白名单事件，无关信息不下发 | D-0012 §4.3 / D-0013 §5 |

## 决定与依据

- 重连 = 快照 + 补齐事件、禁止本地推断：D-0010 / 架构 §5
- 信息只在服务端下发方向校验：D-0012 §4.3
- 防场外（不泄露活动数量）：D-0013 §5
- 取证来源：批次 E7 第 11 步探针（`artifacts/web/batch-run.log`；与 `28-room-health-cleared.png`
  同一次真机会话），玩家页文本"重连补齐有缺口：本地已知 0，快照 198 应补 198 条事件，实际收到 4 条"。
