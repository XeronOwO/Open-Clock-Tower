# 初始身份随机器：按官方阵营分布自动配板

- Status: Todo
- Priority: High
- 来源：用户会话提出（本票无实现；R-0035 已把它登记为"独立能力，要做须先立票据"）
- Depends on: R-0035（阵型修正的现有承载口径）；D-0017（分配即事件）；D-0008 / D-0011（随机只作显式输入）；
  花名册数据（当前只在前端 `web/src/display/labels.ts`，需要服务端权威落点或显式输入边界）

## 要解决的问题

开局分配现在完全手工：宿主 / 说书人把角色逐个分给席位（D-0017），平台既不知道
「多少人该有几个镇民 / 外来者 / 爪牙 / 恶魔」，也没有一键配板——线下要自己建盲抽袋、
自己数分布、自己处理阵型修正，线上只承担"记下来"。本票把它做成平台能力：

1. **按官方阵营分布配板**：给定人数 N，按官方「人数 → 镇民 / 外来者 / 爪牙 / 恶魔」分布表
   生成合法配板；
2. **阵型修正参与配板**：角色标记上的 `[...]` 设置调整（如方古 `[+1 外来者]`）
   只作用于初始设置；**修正可能来自任意类型**——恶魔（当前《梦殒春宵》只有方古）、
   爪牙（其它剧本的男爵一类 `[+2 外来者]`）、镇民 / 外来者都可能有，
   且方向可正可负。配板必须按**修正后的净分布**生成，不是先按基线配完再补一句提示；
3. **随机可重放**：随机只作为**显式输入**（种子或抽取结果）落进分配；
   内核不摇随机、重放不重摇（D-0008 / D-0011）；
4. 说书人仍然保留自由裁量：随机是**建议**，可重摇 / 手改后提交，最终以显式分配为准（D-0002）。

## 验收矩阵

| # | 场景 | 期望 | 证据 |
|---|---|---|---|
| 1 | 官方分布表 | 5–15 人逐点给出各类型数量；表本身有来源（百科页名 + 抓取日期）与版本口径 | 规则单测 + 来源登记 |
| 2 | 阵型修正叠加 | 任意类型角色的 `[...]` 修正参与净分布计算；正负修正、多个修正同时在场都成立 | 规则单测（逐条修正 × 组合） |
| 3 | 修正超池 / 冲突 | 外来者数超出剧本可用外来者、或修正互相冲突时**显式失败**（不静默改写、不悄悄降级） | 失败路径单测 + 文案 |
| 4 | 随机可重放 | 随机结果作为显式输入进分配事件；同一事件流重放产出同一配板，重放不重摇 | 内核 / 集成用例（重建对比） |
| 5 | 角色唯一与席位 | 同一角色最多一个、总席位 = 人数、逐席分配；重复抽取不产生重复角色 | 规则单测 + 真机装置 |
| 6 | 说书人裁量 | 一键随机后可重摇 / 手改；提交仍走既有分配命令面（D-0017），不新增第二套分配路径 | 真机装置截图 + 命令面结构审查 |
| 7 | 信息隔离 | 配板结果只说书人可见；玩家只知道自己那一席（D-0012） | 零信任装置 + 投影用例 |
| 8 | 端到端 | 真机：一键配板 → 开夜 → 首夜角色按配板被唤醒 / 信息只到本人 | 装置截图逐张复核 |

## 决定与依据（开工前必须定稿的三件事）

- **分布表来源**：官方分布表按百科页名 + 抓取日期登记进 `docs/standard/sources.md`；
  表只做数据、不写死进代码分支（不同剧本 / 人数共用同一份数据口径）。
- **修正口径**：净分布怎么算（基线 ± 修正、替换口径与方向）、超池 / 冲突的显式行为，
  以及"修正只影响初始设置、不进引擎判定"的边界（R-0035 第 3 条延续）——需要一条新裁定
  登记进 `docs/standard/rulings.md`，代码注释引用它。
- **花名册权威数据**：现在 `web/src/display/labels.ts` 是唯一一份角色数据（含 `setupModifier`），
  服务端没有；随机配板不能建立在"前端提交什么就是什么"的沙地上。
  先定稿权威落点（服务端花名册数据或明确的输入契约），避免两份数据漂移。

## 非目标

- 不做"配板后自动开局"；不替说书人决定要不要用随机结果（D-0002）。
- 不做跨剧本混搭配板（另见 `future/cross-script-extension.md`）。
- 不改规则引擎的结算路径；不新增"随机"这一内核输入类型——随机仍只以显式分配结果进事件流。
