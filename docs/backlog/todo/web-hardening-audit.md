# 上线就绪性审计：把"能跑"和"敢放公网"之间的差距逐条查出来

- Status: Todo
- Priority: **High**（这是 `web-hardening-programme.md` 的第一步：不查清差距就动手，等于继续打补丁）
- Depends on: 无（只读审计，不改产品代码）

## 为什么要做这一票

需求方 2026-10-06 的当面判断，原文照录：

> 「像登录功能、状态保持、jwt 认证鉴权、加盐哈希这种都是最最基础的网站功能啊……
> 这部分不好好做，那你网站的安全性怎么保证？这玩意可是放公网的，而且未来是开源社区共享使用的，
> 你这么做怎么可能让人放心使用？我们最初快速做核心功能，把这一整块框架都丢下了，
> 甚至还宣称"基本完成"，这是极其不负责任的表现。」

这个判断成立。此前所有工作都围绕**规则内核 + 两端交互**，账号与安全只做到"能登录、能认人、够小圈子自用"，
从未按"公网 + 开源给陌生人用"的标准过一遍。已暴露的症状只是冰山一角：
刷新掉登录、首页不显示身份、换面回到错误的落点——**这些都是审计该一次性查出来的东西**，
不该由需求方一个个撞见。

## 这一票交付什么

一份**可执行的差距清单**：每条 = 现状（代码/配置证据）+ 差距 + 影响面 + 严重度 + 修法建议 + 验证方式。
没有证据的条目不许进清单（不许写"可能不安全"这种）；查不出问题的维度也要写"已核对、无差距"，
否则读者无法判断是"没问题"还是"没查"。

## 审计维度（一个维度 = 一节，缺一节算没做完）

| # | 维度 | 要回答的问题 |
|---|---|---|
| A1 | 账号与口令 | 哈希算法/参数/盐/升级路径是否达标？口令与登录名策略是否合理？恢复码机制是否安全（熵、一次性、轮换、时序）？账号能否注销、改名、多设备并存？ |
| A2 | 会话与状态保持 | 会话在哪、活多久、怎么撤销、进程重启怎么办、刷新/换标签页/换设备各自什么行为？有没有"记住我"？极限情况（并发登录、会话表膨胀、时钟回拨）如何？ |
| A3 | 传输与部署 | 是否强制 HTTPS？有没有安全响应头（HSTS / CSP / X-Content-Type-Options / Referrer-Policy / 权限策略）？反代是否传递真实 IP？限流、超时、请求体上限？明文链路上传了什么？ |
| A4 | 授权与越权 | 每个 Hub 方法**逐个**列出"谁能调"，核对服务端是否真的拦（不能只看前端不显示按钮）。重点：桌主身份、席位归属、说书人权限、跨桌越权、凭据重放、幂等键是否可被他人占用。 |
| A5 | 滥用与风控 | 登录失败限速/锁定、注册滥用（批量注册）、开桌配额、单连接资源上限、超大载荷、公告/注记等自由文本的长度与频率上限。有没有审计日志（谁在什么时候登录/改口令/开桌），日志里会不会混进秘密？ |
| A6 | 数据层 | 只用 `EnsureCreated` + 启动守卫补列能撑多久？需不需要真正的 migration？备份与恢复是否有脚本与被验证过？数据保留与删除（账号注销、桌回收、事件流体积增长）？ |
| A7 | 运维与可观测 | CI（本地三条门禁目前只在本机跑）、健康检查语义、日志分级与轮转、崩溃自动重启已具备吗、部署回滚、磁盘与水位的告警、单进程重启对正在进行的对局意味着什么？ |
| A8 | 开源与合规就绪 | LICENSE 之外还差什么：README 上手路径、配置样例与秘密管理（现在口令/地址怎么放的）、贡献指南、行为准则、安全策略（漏洞怎么报）、隐私说明（收集了什么、留多久）、版本与发布流程、第三方素材许可（百科图热链的口径）。 |
| A9 | 前端体验一致性 | 登录态在四个面之间的呈现是否一致（首页谁都不认识我）、刷新/返回/直接粘地址的行为是否可预期、错误提示是否说人话、手机端可用性、无障碍（键盘可达、标签语义、对比度）。 |
| A10 | 代码与架构 | 按项目自己的硬约束复查：文件行数门禁、职责单一、控制面/数据面分离、**有没有为了赶功能留下的"临时直路"**（直读库的装置、硬编码、TODO/FIXME 清点）、依赖版本与已知漏洞（NuGet/npm 审计）。 |

## 审计怎么做（方法，不是口号）

1. **只读**：不改产品代码；要动手验证的（如"未登录能否调 Hub 方法"）用`tools/` 下的一次性探针，
   探针用完删掉，读数写进清单。
2. **以运行证据为准**：涉及行为的结论必须来自**真跑一次**（真宿主 / 真浏览器 / 真部署），
   不能只看代码推断——本项目已有教训：纸面审查等于没审查。
3. **覆盖反方向**：每个"允许"都要配一条"不允许"的核对（比如"桌主能开夜"要配"非桌主不能开夜"）。
4. **严重度分级**：`Critical`（放公网即出事：越权、明文口令、无鉴权接口）/ `High`（会被刷、会丢数据、
   体验致命）/ `Medium`（该有但可排队）/ `Low`（打磨）。
   每条给"如果不管，最坏会怎样"的具体场景，不写空话。
5. **清单进票据**：审计结果直接写在本票（超出 64KB 就拆 `docs/security/` 一页），
   并由 `web-hardening-programme.md` 逐条转成里程碑任务。

## 审计出报告的门槛（Definition of Done）

- 10 个维度**逐个**有结论：差距条目（带证据）或"已核对、无差距（核对方式见 X）"；
- 每条差距都有：现状证据（文件/命令/读数）· 影响 · 严重度 · 建议修法 · **怎么验证修好了**；
- 严重度汇总表（Critical/High 各几条、都在哪个里程碑处理）；
- 明确写出**本次审计没有覆盖的部分**（例如未做渗透测试、未做并发压测），不许留下"看起来都查了"的错觉。

## 已知的初步线索（审计时逐一证实或推翻，**不许直接当结论**）

| 线索 | 初步观察 | 待证实 |
|---|---|---|
| 口令哈希 | `Pbkdf2PasswordHasher`：PBKDF2-SHA256 / 16 字节随机盐 / 210000 次迭代 / 固定时间比较；用户名不存在时跑假哈希对齐耗时 | 参数是否仍属当前推荐区间（OWASP 口径）、升级路径是否真能滚动 |
| 会话 | `AccountSessionRegistry`：内存、8 小时绝对过期、只存 SHA-256 哈希、可撤销；前端凭据只在 JS 内存 | 刷新即登出（已实测）、进程重启即全掉、会话表是否无上界 |
| JWT | **本项目未使用**，走的是不透明随机令牌 + 服务端会话表 | 需要论证"这比 JWT 更适合本场景"并写进决策，而不是默认省略 |
| 限速 | 未见登录失败限速/锁定 | 需要实测暴力破解成本 |
| 传输 | 目前是明文 HTTP + 明文 WebSocket（真机 `http://`） | 是否上 HTTPS、证书与自动续期方案 |
| 安全响应头 | 未见显式设置（CSP/HSTS 等） | 实测响应头 |
| 迁移 | `EnsureCreated` + 启动守卫补列/删列 | 长期是否需要正式 migration |
| CI | 三条门禁 + 前端 gate 只在本机跑 | 是否需要、放哪 |
